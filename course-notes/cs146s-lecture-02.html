本讲主线 提示词既是让 LLM 做事的通用语言，也是给它编程的方式。本讲指出提示「既是艺术也是科学」——黑箱性质带来一些「魔法」，但存在一批被实证验证的技术：零样本 → K-shot（上下文学习）→ 思维链（多样本/零样本）→ 自洽性（多次采样投票，模型集成）→ 工具使用（最重要的降幻觉/赋能自主性手段之一）→ RAG（注入上下文、自带引用与可解释性）→ Reflexion（让模型反思并修正输出）。最后给出三条最佳实践：结构化格式、明确具体、大胆使用角色提示。

1 提示词背景

提示词（Prompts）是让 LLM 按我们意愿行动的通用语言（lingua franca），也是有效地「给它们编程」的方式。（图示致谢 Andrej Karpathy）

一个类比 想一想我们是如何改变与搜索引擎交互方式的——从简单关键词到结构化的表达，提示词与模型的交互方式也在演进。
  • 提示既是艺术也是科学（both an art and a science）。
  • LLM 的黑箱性质，让「与 LLM 低语」（LLM-whispering）带有一些魔法色彩。
  • 但确有一批被实证验证、能提升 LLM 表现的技术。

【来源：原始课件 第 3–5 页】

2 基础提示技术

2.1 零样本提示（Zero-shot）

  • 直接让 LLM 做一件事：没有额外支撑、没有示例。
  • 示例：「写一个 Rust 的 for 循环，遍历字符串列表，只打印偶数索引处的值。」

【来源：原始课件 第 6 页】

2.2 K-shot 提示 / 上下文学习

  • 让 LLM 做事，同时给它若干「怎么做」的示例；有时称为上下文学习（in-context learning）。
  • k 常取 1、3、5（有实证结果支持这些数字）。
  • 最适合推理步骤不多的任务。

3 思维链（Chain-of-Thought, CoT）

  • 为给定任务展示推理步骤。
  • 多样本 CoT（Multi-shot）：写出推理轨迹作为示例。
  • 零样本 CoT（Zero-shot）：「Let's think step-by-step（让我们一步步思考）」。
  • 用显式的 <reasoning> 标签要求推理。
  • 最适合有多个逻辑步骤的任务：编程、数学。

【来源：原始课件 第 9 页】

3.1 多样本 CoT 示例

任务：「写一个函数判断一个数是否既是完全立方数又是完全平方数。」提示中加入「先提供你的推理」，并附上推理示例：<example>写函数找列表最大元素。步骤：用第一个元素初始化变量，遍历列表并比较……</example>；<example>写函数判断回文数。步骤：取数字、反转各位、比较……</example>

【来源：原始课件 第 10 页】

3.2 零样本 CoT 示例

任务：「写一个函数求数组的最长递增子序列。」提示进阶为：「写代码前先一步步思考子问题，并在回答中包含你所考虑的子数组的演算示例。」

【来源：原始课件 第 11 页】

4 自洽性（Self-consistency）

  • 对输出多次采样（通常配合 CoT），聚合最常见的结果。
  • 通过采样多样的推理路径形成一种「模型集成」（model ensembling），减少幻觉与错误答案。

示例：对「这个报错的根本原因是什么」（IndexError: list index out of range）把同一提示运行 5 次，然后取多数结果。

【来源：原始课件 第 12–13 页】

5 进阶技术

5.1 工具使用（Tool Use）

  • 让 LLM 得以「推迟」到它需要交互的外部系统。
  • 是减少幻觉、让 LLM 具备自主性的最重要技术之一。

示例：修复 IndexError 后，要求「确保 CI 测试仍然通过」，并给出可用工具：<tools> pytest -s /path/to/unit_tests；pytest -v /path/to/integration_tests </tools>。

【来源：原始课件 第 14–15 页】

5.2 检索增强生成（RAG）

  • 为 LLM 注入上下文数据。
  • 让 LLM 保持最新（无需重新训练）→ 迭代更快。
  • 免费获得可解释性与引用（citations）。
  • 减少幻觉。

示例：扩展 UserAuthService 以校验客户端是否提供有效 OAuth token——提示中附上当前 UserAuthService 的代码片段 <code_snippet>，以及 requests-oauthlib 文档路径 <url>。

【来源：原始课件 第 16–17 页】

5.3 Reflexion（反思）

  • 让 LLM 反思自己的输出。
  • 把来自环境信号的口头反馈（verbal feedback）通过增补上下文重新注入 LLM。
  • 在环境中采取行动并得到观察后，追加一个提示后缀：「现在批判性地审视你的答案。它正确吗？如果不对，解释原因并重试。」
  • 多轮提示：第 1 轮模型给出初次尝试；第 2 轮你问「那样对吗？如有必要请反思并修改」。

示例（company_location 列需同时支持字符串与 JSON）：单测抛出 JSONDecodeError → 观察（observe）→ 反思「必须确保输入字符串时不抛错」→ 扩展提示（extend prompt）后再改。

【来源：原始课件 第 18–19 页】

6 补充术语：三类消息

消息类型说明
System prompt 系统提示提供给 LLM 的第一条消息（终端用户通常看不到）；设定人设、关于 LLM 输出的规则、风格
User prompt 用户提示来自人的真实请求或指令；目前为止的例子基本都是这一类
Assistant 助手消息LLM 实际生成的内容

7 最佳实践

  • 提示改进工具：Anthropic 的 prompt improver（docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/prompt-improver）。
  • 清晰表达：把提示给一个了解很少的人，如果他都困惑，LLM 也会困惑。
  • 大胆使用角色提示：让系统提示更强大。示例：「你是一个热爱编程的助手，具备高级软件开发者的水平，回答非常细致且讲究细节」；对比「你是个 Gen Z 数字闺蜜，说话像凌晨两点在 Snapchat 上发消息」——角色决定输出风格。
  • 提示要有结构化格式：用标签包裹数据，例如 <log>日志消息</log> 与 <error>栈追踪</error>。
  • 明确说明你要什么：语言、技术栈、库、约束。
  • 拆解任务：把大任务分解为小任务。

【来源：原始课件 第 25–30 页】
