3 Claude Code 如何工作：智能体循环

3.1 起点问题

「当你在 Claude Code 里敲下一句 prompt 时，会发生什么？」——本讲围绕这个问题展开。（课堂互动：举手加分）

【来源：原始课件 第 5 页】

3.2 智能体循环（The Agentic Loop）三步

步骤名称内容承担方（颜色对应原图）
1收集上下文 Gather contextprompt、文件、工具返回的结果harness（外壳）
2生成动作 Generate action决定运行一个工具：bash、read、edit 等model（模型）
3执行工具 Run tool测试、输出、重新读取状态your machine（你的机器）

循环往复：每一步都以上一步返回的内容为条件（every step conditioned on what the last one returned）。

关键结论 一次用户 prompt = 多次模型调用 + 多次工具执行，而不是一次单独的请求。（One user prompt = many model calls and many tool executions, not a single request.）

【来源：原始课件 第 6 页】

3.3 键入之前：上下文已经不小

在你敲下第一个字符之前，上下文（context）就已经有 10k+ tokens。初始上下文构成：

类别内容
SYSTEM 系统Claude Code 的指令
PROJECT 项目环境信息（environment）
MEMORY 记忆持久化的项目 / 用户笔记 / CLAUDE.md
TOOLS 工具Read、Edit、Bash、Glob、Grep、Web、Agent
SKILLS / MCP仅加载名称与描述（names and descriptions）
USER 用户「修复这个失败的 auth 测试」等具体指令

注意：Skill 和 MCP 条目一开始只有名字——只有当 Claude 真正要用它们时，完整文本才加载进上下文。

【来源：原始课件 第 7 页】

3.4 它不会把你的整个仓库发过去

仓库仍然留在磁盘上，Claude 按需（on demand）拉取其中的片段：

步骤动作
1你的仓库：磁盘上成千上万个文件
2Claude 自问：「我需要什么？」
3调用 Grep("authentication")
4只返回少量匹配行
5这一小片（slice）才进入上下文

【来源：原始课件 第 8 页】

3.5 模型提议，外壳执行

角色职责
Claude 模型发出一个动作请求，例如 Bash("pytest")
Claude Code 外壳（harness）解析请求、检查权限、真正执行
你的机器pytest 实际运行，产生 stdout / stderr
回到模型执行结果作为 tool_result 重新进入模型上下文

【来源：原始课件 第 9 页】

3.6 一次用户输入触发多次模型推理

一个用户轮次会展开成「推理」与「工具执行」交替的链条：

符号序列含义
U (prompt)用户输入
M₁ (inference) → T₁ (tool)第一次推理 → 第一个工具调用
M₂ (inference) → T₂ (tool)第二次推理 → 第二个工具调用
… → Mₙ (inference) → A (answer)反复迭代，直到给出最终答案

实战示例（修复会话相关 bug）：pytest → 读 session.py → grep create_session → 编辑 session.py → pytest → 全部通过。每一次请求都以上一次的推理与工具结果为条件。

【来源：原始课件 第 10 页】

3.7 权限层：介于意图与执行之间

工具请求只是一个「提议」，需要你或另一个模型批准。以 Claude 请求 Bash("rm -rf build/") 为例：

权限模式行为
Manual 手动每次询问，由你确认（ask — you confirm first）
Accept Edits接受编辑类操作
Bypass permission绕过权限检查（allowed — 命令直接运行）
Auto 自动由一个小模型检查后决定（denied — 什么都不会发生）

【来源：原始课件 第 11 页】

3.8 上下文增长，然后被压缩

  • 每一步都会增加 token：模型回复、文件内容、命令输出。
  • 典型上下文大小：1M tokens（Sonnet / Opus / Fable、GPT 5.6）；今年早些时候 256K 还很常见。
  • 上下文不是免费的：prefix-cache 的读取占了成本的大头。
阶段说明
Request 1 → N上下文逐轮增长（bar 逐步变高）
COMPACTION 压缩总结旧轨迹，重新注入 CLAUDE.md 与 memory
Request N+1压缩后的上下文重新开始增长

上下文管理是外壳（harness）设计的重要组成部分（下周讨论）。

【来源：原始课件 第 12 页】

3.9 本部分小结：智能体循环

环节要点
Prompt + context提示词与上下文一起进入模型
Model proposes模型提出动作
Harness executes外壳解析并执行
Result folds into context结果折叠回上下文
loop循环重复直到任务完成

【来源：原始课件 第 13 页】

4 记忆（Memory）：从指令到惯例

4.1 记忆让智能体成为可能

智能体 = LLM（推理与规划）+ Memory（记忆）+ Tool / Action（工具 / 动作）+ Observation（观察）+ Environment（环境）。LLM 本身是无状态的（stateless），真正让它成为智能体的是工具与记忆。

【来源：原始课件 第 14–15、27 页】

4.2 上下文是一种记忆

类型含义
Context：工作记忆（Working Memory）模型当前能看到的内容——随会话结束而消失（dies with the session）
Persistent Memory：持久记忆跨会话存活、下次启动时重新加载的内容
  • 智能体在两次运行之间是无状态的——每个会话都从零开始。
  • 实践中的「记忆」就是会话启动时加载的文件（files loaded at session startup）。
  • 金句：每一次创建记忆，都是一个关于「什么东西要被永久重新读取」的决定。

【来源：原始课件 第 16 页】

4.3 为什么智能体需要记忆

「记忆是指令变成惯例（instruction becomes convention）的方式。」

要解决的问题表现
重复指令 Repeated instructions每个会话都要重新解释同一套设置
丢失的决策 / 假设上下文压缩后，「为什么这么做」消失了
重复发现 Repeated discovery智能体反复读同样的文件来重新了解代码布局
行为不一致不同会话做出不同的选择

【来源：原始课件 第 17 页】

4.4 两套承载知识的系统

两者都会在每次会话开始时加载进上下文：

维度CLAUDE.md 文件Auto memory（自动记忆）
谁写你（You）Claude
内容指令与规则（instructions and rules）学到的经验与模式（learnings and patterns）
范围项目 / 用户 / 组织每个仓库，跨 worktree 共享
加载到每次会话每次会话（前 200 行 / 25KB）
用途标准、工作流、架构你的偏好、纠正意见、项目背景

【来源：原始课件 第 18–19 页】

4.5 CLAUDE.md 放在哪里（加载顺序）

文件按范围从大到小加载，最靠近的规则最后被读取（范围最小、优先级最高）：

顺序层级路径与说明
1Managed policy 管理策略…/ClaudeCode/CLAUDE.md · 组织级，不可排除
2User instructions 用户指令~/.claude/CLAUDE.md · 你的偏好，适用于所有项目
3Project instructions 项目指令./CLAUDE.md 或 ./.claude/CLAUDE.md · 通过源码控制团队共享
4Local instructions 本地指令./CLAUDE.local.md · 个人使用，被 gitignore 忽略

【来源：原始课件 第 20 页】

4.6 CLAUDE.md 该写什么

原则 「上下文是租来的，记忆是买下的（Context is rented, memory is owned）」——要审慎决定买下什么。
维度建议 / 内容
Size 大小每个文件 200 行以内
Structure 结构使用 Markdown 标题与列表
Specificity 具体性写具体规则，而不是含糊的约定
Consistency 一致性不要有互相矛盾或过时的规则
✔ 应该包含命令（如何跑测试、构建、linter）；硬性约束（永不提交到 main、永不改生成文件）；智能体难以廉价推断的事实（布局、归属、坑点）
✘ 不该包含模型已懂的语言/框架知识；linter 或 formatter 已强制的风格；长篇散文、变更日志、任何秘密信息

【来源：原始课件 第 21 页】

4.7 太长就拆到 .claude/rules/

  • 一个文件一个主题：每个规则文件只覆盖一个关注点，保持短而具体。
  • 加 paths: frontmatter：只有 Claude 触碰到匹配文件时才加载（不写 paths: 则每次会话都加载）。
  • 示例目录：.claude/rules/ 下放 testing.md、api-style.md、db-migrations.md。
  • 要点：限定范围的规则让上下文窗口保持小；只加载与当前工作匹配的规则；CLAUDE.md 保持精简，细节放在 rules 里。

【来源：原始课件 第 22 页】

4.8 Auto Memory：Claude 自己的笔记

类型字段记录内容
user 用户你的角色、专业领域和工作偏好
feedback 反馈你给出的纠正、你确认过的做法
project 项目正在进行的工作、代码里没有的决策
reference 参考存在于项目外部的信息

存储结构：~/.claude/projects/<project>/memory/ 下有 MEMORY.md、user_role.md、feedback_testing.md 等。

  • 每个文件用一个 type 字段打标签；
  • MEMORY.md 是索引——每次会话加载前 200 行（25KB）；
  • 机器本地存储；worktree 共享同一目录；
  • 默认开启，可用 /memory 关闭。

【来源：原始课件 第 23 页】

4.9 检索使用索引

索引始终加载；主题文件只在相关时才读取。流程：

步骤动作
1会话开始（Session starts）
2加载 MEMORY.md 索引
3识别相关主题
4按需读取主题文件
5把记忆应用到任务

索引让上下文窗口保持小——只读取任务真正需要的那个主题文件。

【来源：原始课件 第 24 页】

4.10 查看与控制记忆的四个命令

命令作用
/memory浏览、编辑、删除或禁用记忆
/context查看加载了哪些指令文件
/init生成一份起始 CLAUDE.md
/doctor识别可能不该放进 CLAUDE.md 的内容

【来源：原始课件 第 25 页】

4.11 记忆的成本

要点说明
每个永久 token 都是「租金」在每次会话开始时支付
与任务竞争同一窗口记忆和任务共用有限的上下文空间
过时记忆比没有更糟它会主动误导（actively misleads）
像对待代码一样对待记忆审阅、裁剪、纳入版本控制
根本原因上下文大小有限，且你为发给 Anthropic 的每个 token 付费

【来源：原始课件 第 26 页】

5 成为可行动的智能体：核心工具

工具作用
Read打开文件、检查状态——使用最多的工具
Searchgrep 与 glob——不用全读就能找到目标
Fetch拉取网页或文档——会把不可信文本带进上下文
Edit / Write修改文件——第一个「有后果」的工具
Shell构建、测试、git——除非沙箱隔离，否则等于整台机器
Delegate派生子智能体——返回一个摘要的工具
  • 用哪些工具由模型自己决定，你不需要做太多干预。
  • 在作业 2 中，你将亲手实现这些工具。

【来源：原始课件 第 28 页】

6 扩展智能体：Skills、MCP、Hooks 与 Plugins

6.1 四种机制，四个不同的问题（不可互换）

机制解决的问题一句话定位
Skill 技能智能体应该如何执行一项任务决定「怎么做」（how）
MCP它能访问哪些外部数据与动作向外连接（reaches outside）
Hook 钩子生命周期事件发生时自动做什么执行强制约束（enforces）
Plugin 插件扩展如何打包与分发负责分发（distributes）
四层结构 一个 skill 决定怎么做，MCP 向外触达，hook 负责强制，plugin 负责打包分发。

【来源：原始课件 第 29–30 页】

6.2 各机制在智能体循环中的挂载点

循环环节挂载的扩展
User request 用户请求—
Model reasoning 模型推理Skill 提供知识与流程
Tool selection 工具选择MCP 提供外部工具
Tool execution 工具执行Hook 可在循环任意阶段检查、阻断或响应
整体打包Plugin 把 skills、MCP servers 和 hooks 打包成一个可安装单元

【来源：原始课件 第 31 页】

6.3 示例：一次发布工作流

任务：准备发布、验证、发布到 GitHub、通知团队。

任务环节对应机制
遵循发布流程（Follow the release procedure）Skill
创建 GitHub releaseMCP
测试失败时阻止发布Hook
分享整套配置Plugin

【来源：原始课件 第 32 页】

6.4 Skill：可复用的流程

技能 = 任务需要时智能体加载的知识与流程。承载内容：领域知识、参考材料、可重复的工作流；可被模型或用户调用；在运行时推理。可以把它理解为「上下文工程」（context engineering）。示例：/release 2.4.0

【来源：原始课件 第 33 页】

6.5 Skill 的结构

组成说明
目录结构.claude/skills/release/ 下有 SKILL.md、references/、scripts/
name / descriptionname: release；description: Prepare a release
description 的作用控制发现（discovery）——模型据此判断何时使用该技能
body 正文承载具体流程；支持文件提供参考资料与脚本
用户直接调用/release

示例流程：1 读发布说明 → 2 确认版本 → 3 跑测试 → 4 准备提交 → 5 发布前询问。

【来源：原始课件 第 34 页】

6.6 Skill 的调用方式与上下文成本

调用模式说明
Model-invoked 模型调用当技能描述与任务匹配时，Claude 自动加载
User-invoked 用户调用用户显式运行 /<skill-name>
  • 成本：描述在会话启动时加载；完整正文只在技能运行时加载。
  • 有副作用的工作流通常应要求显式调用。
  • 清晰、彼此区分度高的描述能减少错误选用技能。

【来源：原始课件 第 35 页】

6.7 MCP：外部能力层

MCP（Model Context Protocol，模型上下文协议）通过一套标准协议把智能体连接到外部服务。它能让 Claude 获得既不在模型里、也不在本地文件里的能力。

典型能力示例
读写 GitHub issues创建 / 更新 issue
查询数据库执行 SQL 查询
检索监控数据拉取指标与日志
访问 Figma 设计稿读取设计信息
发 Slack 消息向频道发送通知
控制浏览器网页自动化

【来源：原始课件 第 36 页】

6.8 MCP 工具调用如何工作（六步）

步骤动作
1Claude 识别出需要某个动作
2MCP 客户端使用一个工具
3MCP 服务端处理连接
4外部服务执行操作
5结构化结果返回 Claude
6Claude 评估结果
与本地工具几乎一样 相同的名字、描述与类型化 schema；相同的「调用—返回」契约；只是运行在另一个进程里。协议负责承载调用，是否调用仍由智能体决定。

【来源：原始课件 第 37 页】

6.9 Hook：生命周期自动化

会话从左向右运行，hook 可以在每个标记的事件点触发：

事件点可做的事
Session start 会话开始加载上下文、记日志
User prompt 用户输入校验或补充
Model reasoning 模型推理无 hook —— 推理不是事件
Before tool use 工具调用前检查或阻断
After tool use 工具调用后格式化、测试、记日志
Before stopping 结束前验证测试

Hook 在事件上触发，可运行命令、HTTP 请求、MCP 工具、prompt 或子智能体。

【来源：原始课件 第 38 页】

6.10 Plugin：打包层

插件 = 一个可安装单元，携带 skills、hooks、agents 与 MCP 配置：

目录项作用
skills/、hooks/、agents/技能、钩子、子智能体
.mcp.json、.lsp.jsonMCP 与 LSP 配置
.claude-plugin/plugin.json插件清单
  • 打包带来的好处：一条命令安装；版本固定；命名空间避免重名；团队复用统一配置；可通过 marketplace 分发。
  • 一句话：插件是把一套可用的配置变成别人也能安装的东西的方式。

【来源：原始课件 第 39 页】

6.11 四种机制如何配合

机制角色
Skill知识与流程（knowledge and procedure）
Claude推理与工具使用（reasoning and tool use）
MCP连接 GitHub、Slack、数据库等外部系统
Hook在生命周期事件触发——每次工具调用前后都可执行
Plugin把 skill、MCP 配置与 hooks 打包，便于安装到其他地方

判断力（judgment）、能力（capability）、强制（enforcement）——以及把三者打包发货的包。

8.1 MCP 是什么、为什么存在

  • 动因：需要访问外部工具与服务。MCP 出现之前是 N×M 的实现问题——每个 AI 客户端都要为每个服务单独做集成。
  • 定义：一个开放的（无状态的）协议，让 AI 应用能够发现并使用外部服务器暴露的能力。
  • 官网：https://modelcontextprotocol.io

【来源：原始课件 第 45 页】

8.3 MCP 的三个核心原语

原语含义示例
Tools 工具Claude 可以调用的动作create_issue(…)
Resources 资源可读的数据——一个 issue、一个 schemagithub://issues/123
Prompts 提示词服务端暴露的可复用提示模板triage_issue(…)
  • Prompt 返回指令：例如「审查 issue #123；判断是否可复现；评估严重性为高；推荐负责人与下一步」。
  • Prompt 由用户控制：应用把它做成命令或菜单项；在 Claude Code 中是带命名空间的斜杠命令，如 /mcp__github__triage_issue 123 high。

【来源：原始课件 第 47 页】

8.5 MCP 安全：最关键的部分

一个已连接的服务器能看到你发给它的内容，并能用你的凭据执行操作。连接前应自问：「这个服务器能读什么、能改什么？」

原则做法
最小权限 Least privilege把 token 限定到真正需要的仓库、表或频道
读写分离 Read vs. write读与写分开；变更操作需经过批准
不信任工具输出永远不要把返回内容当成指令来执行
安装前审查 Vet before installing第三方服务器可能携带提示注入，务必审查

【来源：原始课件 第 49 页】

8.6 什么是 MCP 网关（Gateway）

网关是 AI 客户端与一个或多个 MCP 服务器之间的控制层——类似 API 网关，但说的是 MCP 协议（tools/list、tools/call、resources、prompts、schemas、协议版本）。它是一种架构模式；对客户端来说，网关看起来就像另一个 MCP 服务器。

组件职责
Claude Code / agent客户端
MCP gateway认证 · 策略 · 日志 · 路由 · 限流
后端 MCP serversGitHub MCP、Jira MCP、Database MCP 等

【来源：原始课件 第 50 页】

8.7 网关做什么

功能说明
1 · 聚合 Aggregate一个连接、一个带命名空间的目录：github.*、jira.*、postgres.*
2 · 路由 Route把每次调用转发给对应的服务器；Mcp-Method 头无需读取 body 即可路由
3 · 执行策略 Enforce policy谁可连接、哪些工具可见 / 可调用 / 需要人工批准
4 · 身份代理 Broker identity客户端只认证一次，上游凭据留在网关后面
5 · 观测 Observe集中审计：身份、工具、决策、延迟、结果、成本
6 · 扩展 Scale负载均衡、重试、熔断、目录缓存、配额
  • 什么时候值得用：当许多用户、智能体、服务器、凭据或合规规则需要被一致治理时。
  • 但它也是信任边界：凭据范围过宽、终端用户身份丢失、命名冲突、日志里的秘密、单点故障。
