3 案例研究一：Superpowers（软件开发插件）

Superpowers 是一个软件开发插件（obra/superpowers），安装命令：/plugin install superpowers@claude-plugins-official。它用一个结构化的技能库把「同一个模型」变成遵循严格流程的智能体。

【来源：原始课件 第 5 页】

3.1 同一个模型，不同的工作流

默认（DEFAULT）流程：功能请求 → 直接开始编码 → 迭代修复。Superpowers 流程：0 用户输入 → 1 澄清问题 → 2 批准设计 → 3 写详细计划 → 4 测试驱动构建 → 5 检查验证 → 6 完成或合并分支（PLAN → BUILD → SHIP）。

核心洞察 两个智能体用的是同一个模型和同一套工具——区别只在于指令（instructions）不同。

【来源：原始课件 第 6 页】

3.2 Superpowers 的九个技能

技能 Skill职责 Responsibility
using-superpowers发现和调用技能的规则
brainstorming把请求变成一个被批准的设计
writing-plans把设计拆解为具体任务
using-git-worktrees创建隔离的工作区
test-driven-development强制红—绿—重构（red, green, refactor）
systematic-debugging在提出修复前先找根因
requesting-code-review对照计划检查实现
verification-before-completion报告成功前要求提供证据
finishing-a-development-branch合并、PR、保留或清理

该页在原始课件中标注为选读（OPTIONAL）。

【来源：原始课件 第 7 页】

3.3 Superpowers 架构

仓库布局：.claude-plugin/（plugin.json 元数据）→ hooks/（hooks.json + session-start 会话钩子）→ skills/（技能库：using-superpowers、brainstorming、writing-plans、test-driven-development 等）→ tests/。组件映射：插件元数据、会话钩子、技能库共同决定智能体行为。

要点 插件只是分发容器（distribution container）——真正提供行为的是技能与钩子。

【来源：原始课件 第 8 页】

3.4 一个技能的解剖（Anatomy of a Skill）

目录 skills/brainstorming/ 下有 SKILL.md、visual-companion.md、scripts。SKILL.md 的 front matter 是元数据（name: brainstorming；description: Use before creative work.），正文是工作流：1 检查项目 → 2 分类范围 → 3 澄清需求 → 4 比较方案 → 5 给出设计 → 6 等待用户批准 → 7 调用 writing-plans。

一句话 Front matter 是元数据；正文（body）是智能体遵循的流程。

【来源：原始课件 第 9 页】

3.5 SKILL.md 的六个组成部分

组成部分功能
name稳定标识符
description技能何时适用
Instructions（指令）要遵循的流程；入口条件、必需动作、禁止动作
Checkpoints（检查点）继续之前需要人工批准（human approval gates）
References（参考）只在需要时加载的细节（验证要求）
Scripts（脚本）确定性操作（deterministic operations）

流程型技能还可以定义「下一个适用的技能」（the next applicable skill）——每个技能引导智能体行为，并可指定其后继。

【来源：原始课件 第 10 页】

3.6 为什么仅有技能不够

安装技能只是让它们可用（available）——可用并不保证智能体一定会去查看它们。Superpowers 用 hooks/hooks.json 里的 SessionStart 钩子（matcher: startup|clear|compact，type: command，command: run-hook.cmd，async: false）来保证：每个会话都确定性触发、在智能体行动之前运行、在 clear 与 compaction 之后重新运行。

【来源：原始课件 第 11 页】

3.7 会话启动脚本（Session-Start Script）

hooks/session-start（简化）：定位已安装的插件 → 读取引导技能 using-superpowers/SKILL.md → 对 Markdown 做 JSON 转义 → 作为 hookSpecificOutput.additionalContext 返回 → Claude Code 把它加入上下文。

该页为选读内容。

【来源：原始课件 第 12 页】

4 案例研究二：Caveman（双向 token 压缩插件）

Caveman 展示了五种扩展机制外加一个本地代理（local proxy）。安装：claude plugin marketplace add JuliusBrussee/caveman → claude plugin install caveman@caveman。

【来源：原始课件 第 15 页】

4.1 为什么要压缩智能体的 token

  • 上下文会满：日志、diff 和工具输出把真正的工作挤出去。
  • 每一轮都要付费：token 双向都要付钱、要等待。
  • 压缩会丢细节：太晚裁剪上下文会丢掉重要的东西。

示例：测试输出原本 786 行（含 776 行冗余），压缩后模型只读到「3 tests fail: ETIMEDOUT at client.ts:88」。原则：双向压缩——并保留原文可供随时检索。

【来源：原始课件 第 16 页】

4.2 双向压缩：技能改「写」，代理改「读」

方向机制作用
输出 AGENT OUTPUT响应技能（Response skill，提前注入上下文）改变模型如何写——报告 输出 token 减少 65%
输入 AGENT INPUT本地代理 + 引擎（Local proxy + engine）改变模型读到的内容——压缩日志、diff、文件等
注意 技能本身会增加输入 token，因此整场会话的净节省要低于 65%。用法：/caveman ultra，然后「Run the tests and explain the failure.」

【来源：原始课件 第 17 页】

4.3 一个例子的执行顺序

步骤动作
1钩子保存 ultra 模式
2钩子注入简洁回复提醒
3智能体执行命令（来自 LLM）
4Caveman（代理）压缩嘈杂的测试输出
5模型收到压缩后的上下文
6模型返回简洁诊断
7MCP 按需检索原文

【来源：原始课件 第 18 页】

4.4 Caveman 的插件打包

仓库结构：.claude-plugin/plugin.json、skills/（caveman、-commit、-review、-compress、-stats）、commands/、src/hooks/、mcp/、proxy/、engine/、agents/。插件清单在 SessionStart 挂 caveman-activate.js，在 UserPromptSubmit 挂 caveman-mode-tracker.js。

【来源：原始课件 第 19 页】

4.5 响应技能：让输出更简洁

skills/caveman/SKILL.md：描述为「Compressed mode」。保留（Preserve）：技术术语、命令、路径、代码、错误、数字、单位、否定；移除（Remove）：填充词、重复、客套、模糊表达；短句、主动语态。它改变的是智能体的沟通方式。

【来源：原始课件 第 20 页】

4.6 命令：显式用户控制

命令作用
/caveman激活默认 full 模式
/caveman ultra最大压缩
/caveman off停用该风格
/caveman-commit / -review / -compress / -stats / -help简洁提交信息 / 审查意见 / 压缩记忆文件 / 会话统计 / 可用操作

【来源：原始课件 第 22 页】

4.7 钩子：让提示词时的一次选择持久化

钩子职责
SessionStart（caveman-activate.js）决定本会话模式；安全存储模式状态；把规则作为隐藏上下文注入；压缩后恢复规则；清理旧状态并提供状态行
UserPromptSubmit（caveman-mode-tracker.js）检查每条用户 prompt；检测 /caveman ultra 与「normal mode」等短语；更新会话模式；在聚焦操作后恢复模式

SessionStart 初始化行为；UserPromptSubmit 在对话中途检测变化。

【来源：原始课件 第 23 页】

4.8 MCP：把压缩暴露为可调用工具

五个 MCP 工具功能
caveman_compress压缩 + 返回恢复句柄（recovery handle）
caveman_retrieve逐字节还原原文（byte-exact original）
caveman_stats压缩统计
caveman_toon_encode / decodeJSON 转 TOON / TOON 转回 JSON

【来源：原始课件 第 24 页】

4.9 代理：压缩模型读到的内容

链路：编码智能体 → 本地 Caveman 代理 → 模型提供方。类型感知压缩（Type-Aware Compression）保留：日志（错误、栈追踪、首尾）、代码（import、签名、类型、函数体）、diff（文件与 hunk 头、改动行）、JSON（键、结构、错误子树）、搜索（高价值匹配、诊断）、HTML/文本（标题、相关章节）。

对比本地代理MCP
调用方式拦截每一个请求只在被调用时运行
位置位于智能体与提供方之间位于其旁边
影响能改变上下文不能改变上下文
为什么必须用代理 钩子能拦截请求，但无法透明地重写发给 LLM 的请求——因此需要代理。（如果你自己写 harness，则另当别论。）

【来源：原始课件 第 25 页】

4.10 Caveman 中各能力的分工

机制角色
Skills简洁风格、聚焦工作流
Hooks激活、追踪、强化模式
Commands选择模式、请求操作
MCP压缩、检索、统计、编码
Plugin打包 Claude Code 集成（一次安装与更新单元）
Local proxy拦截发往模型提供方的请求

【来源：原始课件 第 26 页】

5 用多智能体成为 100x 工程师

核心问题：「如何在两小时内完成作业？」答案是把工作交给多个并行、长时运行的智能体。常见形态：子智能体（Subagent）、智能体团队（Agent team）、动态工作流（Dynamic Workflow）——智能体并行铺开，账单也并行增长（Agents fan out in parallel. So does the invoice.）。

【来源：原始课件 第 27 页（PDF 第 26–27 页）】

5.1 扩展的三个维度（Three Axes of Scaling）

维度做法买到什么
并行智能体 Parallel agents — 广度运行多个独立任务，各自在隔离的工作树中吞吐量：缩短墙钟时间，而非提高答案质量
子智能体 Subagents — 广度与深度把有界任务委派给全新上下文，拿回摘要吞吐量与专注：父智能体看不到中间的杂乱
长时运行智能体 Long-running — 时长让一个更大的任务跨越许多步骤范围：更少干预完成更多工作
总结 智能体团队与动态工作流把三者结合起来。

【来源：原始课件 第 28 页】

5.2 手工并行：一个会话一个 git worktree

每个任务一个会话，各自在自己的 git worktree（独立工作目录与分支，共享仓库历史）中：claude -w feature-payments（终端 1 建功能）与 claude -w bugfix-auth（终端 2 修 bug）。一个会话的编辑不会碰到另一个的文件——无需 stash，也无需第二次 clone。桌面应用中每个新会话会自动获得一个 worktree。

【来源：原始课件 第 29 页】

5.3 Git Worktree：一个仓库，多个工作目录

一个 .git（历史、分支、对象、远程）对应多个检出：../repo-main（main 分支，Agent 1 review）、../feat-auth（feature/auth，Agent 2 build）、../fix-flaky（fix/flaky-test，Agent 3 debug）。一份共享历史、三个检出，无需切分支、无需 stash。

【来源：原始课件 第 30 页】

5.4 手工并行的极限

  • 计划在你脑子里：每次交接与下一步都靠你记着。
  • 会话互相看不见：发现只能靠你人工搬运。
  • 分支由你协调：合并顺序与冲突要你自己解决。
  • 无法复现：这次运行没有被记录下来以供重跑。

3 个会话你还能hold住计划；20 个会话你需要「自己的克隆」。

【来源：原始课件 第 31 页】

5.5 子智能体（Subagents）：为什么

子智能体是拥有自己上下文窗口、工具与权限的专用助手。理由：

  • 保留上下文：日志、搜索结果、文件转储不进入主对话。
  • 强制约束：限制可用工具与所用模型。
  • 随处复用：针对某领域的聚焦 prompt，跨项目跨团队共享。
  • 并行化：独立子任务并发运行，总时间取决于最慢的一个（如同时跑 style-checker、security-scanner、test-coverage）。
  • 控制成本：把任务路由到更快更便宜的模型（如 Haiku）——在子智能体 front matter 里写 model: haiku。

【来源：原始课件 第 32 页】

5.6 内置子智能体

内置智能体说明
Explore只读搜索代码库；禁止 Write/Edit；每次调用可设 thoroughness
Plan在 plan 模式做调研，使探索不进入主窗口
General-purpose需要探索与行动的复杂多步工作

Explore 与 Plan 会跳过 CLAUDE.md 与 git status 以保持快速、低成本。

【来源：原始课件 第 33 页】

5.7 定义一个子智能体

子智能体就是一个带 YAML front matter 的 Markdown 文件，正文成为系统提示。示例 .claude/agents/code-reviewer.md：name: code-reviewer；description: Reviews code for quality；tools: Read, Glob, Grep；model: sonnet；正文是「You are a code reviewer...」。放在 .claude/agents/ 为项目级（纳入版本控制，团队共享）；放在 ~/.claude/agents/ 为用户级（跨所有项目）。

【来源：原始课件 第 34 页】

5.8 嵌套子智能体

父智能体的 front matter 中 tools 必须包含 Agent，它才能派生子智能体（如 name: my-orchestrator，tools: Read, Grep, Agent，model: claude-sonnet-5-0）。允许最多 5 层嵌套；2–3 层是最佳区间（sweet spot）。

【来源：原始课件 第 35 页】

5.9 多层子智能体的常见模式

层级角色
Level 0主智能体——持有计划
Level 1实现子智能体、调试子智能体、代码审查子智能体
Level 2测试编写子智能体、验证子智能体

每一层都以全新上下文开始，只返回摘要。

【来源：原始课件 第 36 页】

5.10 与子智能体协作的三种方式

方式说明范围
自然语言在 prompt 中点名子智能体（「Use the test-runner subagent to fix tests」），由 Claude 决定是否委派一次性 ONE-OFF
@-mention选中某个子智能体，保证它会运行（@agent-code-reviewer look at auth changes）单个任务 ONE TASK
--agent 标志整个会话采用该智能体的 prompt、工具与模型（claude --agent code-reviewer）整个会话 WHOLE SESSION

自动委派会自行发生——当它没有发生时，再显式升级控制。

【来源：原始课件 第 37 页】

5.11 该用子智能体还是主对话？

留在主对话委派给子智能体
反复来回迭代不会复用的冗长输出
共享上下文的多个阶段工具或权限需要限制
快速、定向的修改自包含、只返回摘要的工作
延迟敏感并行独立的工作
简单工作可交给小模型

子智能体从零开始：看不到历史，且需要付出收集上下文的延迟成本。若想要在主上下文中复用工作流，应使用技能（Skill）。

【来源：原始课件 第 38 页】

5.12 智能体团队（Agent Teams）

多个 Claude Code 会话协同工作：一个 lead（组长）+ 多个 teammates（组员）。适用场景：审查（组员从不同角度探查并互相质疑）、独立模块（各管一块）、调试（并行检验相互竞争的假设更快收敛）、跨层（前端、后端、测试各由一人负责）。

代价与限制 不是免费的：协调开销与 token 成本随团队规模增长。顺序任务、同文件编辑或重依赖场景——用单会话或子智能体。该功能为实验性，默认关闭。

【来源：原始课件 第 39 页】

5.13 团队的构成与通信

部件说明
Team lead主会话：派生组员、协调工作、综合结果
Teammates独立的 Claude Code 实例，各有自己的上下文窗口
Task list共享工作项，组员认领并标记完成

5.15 动态工作流（Dynamic Workflow）

动态工作流是一个 JavaScript 脚本，在后台编排大量子智能体。当任务需要的智能体数量超过一个对话能协调的范围时使用（如全代码库 bug 扫描、500 文件迁移、交叉验证的研究、多角度的方案）。两种启动方式：在 prompt 里输入 ultracode，或 /effort ultracode 让 Claude 自行决定。两条路径都会派生大量子智能体——规划、设计、实现、审查。

【来源：原始课件 第 44 页】

5.16 让单个智能体跑得更久：/goal 与 /loop

机制说明
/goal交出一个可验证的终态（如 /goal "npm run lint exits with zero errors"）。定义完成条件 → 每次尝试后评估器复查 → 目标达成或 --max-tries 用尽即停止。必须「可验证」：「所有集成测试通过」可以，「重构代码」不行。
/loop按计划重复运行一个 prompt，直到你停止（如 /loop 5m "check CI, fix whatever broke"）。它是触发器而非测试：交出的是时间间隔；你在两次运行之间按 Esc 结束；可在 .claude/loop.md 里放默认 prompt。
关键区别 /goal 在条件成立时停止；/loop 在你要求它停时停止。

【来源：原始课件 第 45–46 页】

5.17 小结：六种放大方式

分类方式要点
同时用更多智能体手工并行智能体你自己负责协调合并
同时用更多智能体子智能体Claude 委派，结果回到它
同时用更多智能体智能体团队lead 通过共享清单管理同伴
同时用更多智能体工作流由脚本持有计划，而非对话
一个智能体跑更久/goal运行到可验证的终态成立
一个智能体跑更久/loop按计划重跑，直到你停止

6.1 16 个智能体如何协调

  • 朴素的基建：容器、Git 与文本文件完成编排。
  • 隔离：每个智能体在独立容器与 Git checkout 中工作。
  • 认领任务：通过简单的锁文件（lock files）。
  • Git 作为协调与集成层：没有聊天，也没有经理智能体。
  • 新会话恢复上下文：读取进度文档（progress docs）。
  • 专家智能体：文档、性能、质量、去重各司其职。
  • 进度信号：自动化测试给智能体反馈。

【来源：原始课件 第 49 页】

6.2 Git 作为协调层

循环：读仓库（clone、扫文档与日志）→ 认领任务（current_tasks/ 中的锁文件）→ 在自己的容器中实现与测试 → 先 pull 所有人再 merge、push、解锁。循环往复，智能体自己挑下一个显然的任务，Git 解决重复认领。冲突自行解决（同一任务被认领两次？一个智能体转向别的）；工件承载上下文（README、进度文档、CI 失败信息让新会话快速进入状态）。

【来源：原始课件 第 50 页】

6.3 成功但不完美

7 编程 / 软件 3.0

7.1 Programming 3.0：从「编程硬件」到「表达目标」

范式链路说明
Programming 1.0（编程硬件）Human → 显式机器指令或汇编 → Hardware人直接写机器指令
Programming 2.0（编程语言）Human → 编程语言 → 编译器 → 机器指令 → Hardware人写高级语言，编译器翻译
Programming 3.0（表达目标）Human → 自然语言 → Agent → 编程语言 → 机器指令 → Hardware人表达目标，智能体补全中间层

这是授课教师自造的术语，与 Andrej（Karpathy）的定义不同（见下一节）。总体趋势：生产力更高（Higher productivity），不确定性更大（More uncertainty）。

【来源：原始课件 第 53 页】

7.2 Software 3.0（Karpathy 的定义）

范式程序是什么？如何创建？
Software 1.0源代码人写 Python / C++
Software 2.0神经网络权重收集数据 + 优化（human → data → optimizer → neural network）
Software 3.0LLM prompts（语言 / 上下文）自然语言（human → language/context → LLM → action）
工程要点 知道在 1.0、2.0 与 3.0 之间该把边界画在哪里，是一项重要的工程技能。

【来源：原始课件 第 54 页】

7.3 不确定性成为核心主题

「不确定性成为核心主题，你必须学会与它共处。」

金句 不要指望智能体是确定性的；要让周围的系统变得可靠。（Do not expect the agent to be deterministic; make the surrounding system dependable.） autonomy 越高，不确定性与风险越高——让自主性与风险相匹配。

【来源：原始课件 第 55、60 页】

7.4 不确定性是新的吗？

不确定性来源Programming 2.0Programming 3.0 新增2.0 的应对之道
硬件 Hardware架构差异：32/64 位、字节序GPU 计算：非确定性内核、浮点方差定宽类型、交叉编译、虚拟化
环境 Environment并发、不可靠网络代码生成时就与环境交互内存一致性模型、幂等 API
软件 Software编译器版本、依赖漂移编译器与模型：不同内核、采样升级前全面测试

「同样的源代码 ≠ 同样的输出」早在很久以前就发生了。

【来源：原始课件 第 56 页】

7.5 从意图到结果：更多的不确定性

1.0/2.0 链路：人（PM）→ 需求 → 程序员 → 环境、记忆 → 程序 → 结果（形式化验证在此发挥作用）。3.0 链路：人 → 需求 → LLM 智能体 → 环境、记忆 → 程序 → 结果。新增的不确定性：单一 prompt 带来的输入歧义（被忽略但实际存在），需要更多研究。

【来源：原始课件 第 57 页】

7.6 与不确定性共处：不确定性来自哪里

环节不确定性
自然语言语义不确定性（semantic uncertainty）
检索 / 上下文检索漂移：索引更新、分块、上下文截断
模型生成概率波动：① 采样 ② 软件与硬件的非确定性
智能体 / 工具循环轨迹与环境非确定性：工具失败、环境变化
生成的程序生成后通常是确定性的——除非运行时调用模型或工具

【来源：原始课件 第 58 页】

7.7 编程 / 软件 3.0 的最佳实践

阶段实践做法
1 · DEFINE 定义 upfront 声明假设让模型在执行前确认任何含糊之处
2 · CONTROL 控制把提议与执行分离智能体提出计划；任何提交前先验证
2 · CONTROL 控制显式管理上下文拥有记忆、来源与检索；让过期信息失效
2 · CONTROL 控制指定结果而非 prompt给出需求、不变量、约束与验收测试
3 · VERIFY & GOVERN 验证治理收紧「生成—验证」循环廉价而频繁的检查胜过最后一次昂贵审查
3 · VERIFY & GOVERN 验证治理再深一层地度量创建测试、度量多指标、构造可推理的合成负载
