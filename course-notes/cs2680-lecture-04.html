2 ReAct 循环与智能体循环

2.1 ReAct：在一个循环里推理与行动

ReAct = Reasoning + Acting，把「推理」与「行动」放进同一个循环。三步交替：

  • Thought 思考：我知道什么、缺什么、下一步做什么？
  • Action 行动：发出一个环境可以执行的结构化调用。
  • Observation 观察：环境用事实回应。

循环直到观察回答了问题——或停止规则（stopping rule）结束本次运行。

方式问题
Reason only 只推理没有人检验推理；小错误累积成自信的幻觉（confident hallucination）
Act only 只行动工具调用背后没有计划；模型会不断重复自己
ReAct思考引导下一步行动；观察修正下一步思考

参考：arxiv.org/pdf/2210.03629。

【来源：原始课件 第 4 页】

2.2 智能体循环的代码骨架

一个最小智能体循环：把 system 指令与 user 请求放进 messages；每步 call_model(messages, tools) → 追加模型消息 → 若 final_answer 则返回 → 否则遍历 tool_calls，validate 参数、execute_tool、把结果作为 role=tool 的消息追加；超过 MAX_STEPS 抛异常。

三处设计动作 作为外壳设计者，你要做的是：① 组装上下文（assemble the context）；② 校验请求、检查权限并执行；③ 可选地处理结果并管理上下文。加上「编写工具定义」（write tool definitions）。

【来源：原始课件 第 5–6 页】

2.3 编码智能体的三个组件（协同设计）

组件说明一句话
01 模型 + 智能体循环LLM 提出动作、看到结果、重复直到完成智能体 = 模型 + 循环
02 工具与护栏搜索、读、改、跑测试与 shell——位于权限、沙箱与批准之后工具决定能力；护栏保证安全
03 状态：上下文与记忆窗口里现在有什么，加上跨步骤携带的东西组装它；保留能活过这一轮的内容

三个组件共享同一个上下文窗口——必须一起设计。

3 工具设计（一）：搜索与读取代码

核心问题：智能体该提供哪些工具？如何找到相关代码？（课堂互动：举手加分）

【来源：原始课件 第 8–9 页】

3.1 glob 与 grep（词法搜索）

  • 智能体循环使用 ls、glob、grep——无需构建任何东西，也无需保持同步。
  • 始终反映仓库的实时状态（live repo）。
  • 代价：消耗轮次与上下文；词法匹配会漏掉意译（paraphrase）。

示例「fix the login timeout」：① grep -rn "timeout" src/ → 12 个文件 37 处命中；② glob src/**/auth/*.ts → 缩小到 auth/retry.ts；③ 读取并打补丁 RETRY_MS = 500。

【来源：原始课件 第 10 页】

3.2 语义搜索（Semantic search）

  • 语义：把代码块做 embedding，按含义检索（意思相同、用词不同 → 向量接近）。
  • 结构：文件树 + 排序后的符号（Aider 的 repo map，文件/类/签名的分级大纲）。
  • 查询时快；代价是构建与重新同步索引。

示例：「where do we rate-limit?」第一次查询就返回 throttle.ts。

【来源：原始课件 第 11 页】

3.3 外部信号（Extrinsic signals）

  • 源码之外的证据：栈追踪、失败的测试、git 历史。
  • 调试时精度最高的信号（highest-precision signal）。
  • 只有在存在这类信号时才有用。

示例（checkout 崩溃）：① 读信号 stack trace: cart.ts:88；② 打开相关栈帧 read tax.ts:20-60，发现 applyTax 的舍入问题；③ 打补丁并重跑 pytest → 全绿，完全没用搜索。

【来源：原始课件 第 12 页】

3.4 语言服务器（LSP）

  • 查询编译器的索引：定义、引用、符号、类型。
  • 能解析 grep 只能猜测的 import、重载与重命名。
  • 代价：每种语言一个常驻服务器；冷启动慢。

示例（把 charge() 改名为 capture()）：① textDocument/references → 7 个文件 42 处调用；② textDocument/rename → 包含别名 import；③ 类型检查 → 无未解析符号。

【来源：原始课件 第 13 页】

3.5 四种搜索方式对比

方式如何找代码最适合主要代价
glob / grep字面名字与路径名字已知或可猜每次搜索消耗轮次与上下文
语义索引嵌入块的含义用词与代码不匹配构建与重新同步索引
外部信号追踪、失败测试、git 历史已有报告指向代码只对部分任务存在
语言服务器编译器的符号图编辑必须跟随引用每种语言一个常驻服务器
实践建议 从 grep 开始；当名字不够用时再求助于索引或 LSP。（In practice — start with grep; reach for an index or LSP when names run out）

【来源：原始课件 第 14–15 页】

4 工具设计（二）：编辑代码

核心问题：智能体该如何编辑代码？（课堂互动：举手加分）

【来源：原始课件 第 16 页】

4.1 整文件重写（Whole-file rewrite）

  • 模型重新生成整个文件，工具直接覆盖。
  • 不用纠结补丁语法——每次编辑都能干净地应用。
  • 代价：输出随文件大小增长；未触碰的代码可能漂移（drift）。

示例：读 client.ts（120 行进上下文）→ 写 client.ts（整文件，改了 4 行）→ 与前一版做 diff，一次成功。

【来源：原始课件 第 17 页】

4.2 Unified diff / patch

  • 模型发出补丁，由单独的工具应用；紧凑、可审阅，是人与 CI 已在用的格式。
  • 代价：行号或上下文漂移时 hunk 会失败。

示例：读 client.ts、api.ts 拿到锚点 → 发出 @@ -41,3 +41,3 @@（6 行、两个 hunk）→ git apply patch.diff，两个 hunk 都应用。

【来源：原始课件 第 18 页】

4.3 搜索替换（Search and replace）

  • 模型发出精确的锚点字符串及其替换。
  • 输出与改动量成正比，而非与文件成正比。
  • 代价：锚点含糊、过期或空白不符时会失败。

示例：grep -n "retries = 3" 找到唯一匹配 → retries = 3 → 5，一次调用无重写 → 读回验证，文件其余部分未动。

【来源：原始课件 第 19 页】

4.4 结构化 / AST 编辑

  • 模型说出对一个符号的操作：重命名、加参数。
  • 不受格式影响；不可能产生无效语法。
  • 代价：需要每种语言的工具；可表达的编辑集合有限。

示例（给 fetchUser() 加 timeout 参数）：add_param(fetchUser)，timeout 默认 5s → 工具改写签名及全部 18 个调用者 → parse + 类型检查，构造上即合法。

【来源：原始课件 第 20 页】

4.5 四种编辑方式对比（token 成本 vs 鲁棒性）

方式主要风险
整文件重写长文件上会漂移（drifts on long files）
Unified diff行号过期时失效（breaks on stale lines）
搜索 / 替换块需要精确且唯一的匹配
结构化 / AST 编辑语言覆盖范围有限

【来源：原始课件 第 21 页】

5 工具执行与其他工具

5.1 Shell：最强也最危险的工具

  • 组合性 Composition：一次调用就能链接、过滤、循环、重试。
  • 可达范围 Reach：文件系统、网络、包管理器、已安装的二进制。
  • 持久性 Persistence：文件与进程活过单次调用。
  • 影响半径 Blast radius：shell 能做什么，智能体就能做什么。

【来源：原始课件 第 22 页】

5.2 执行工具必须考虑的五件事

  • 失败信号（Failure signal）——智能体真正能据以行动的报错；
  • 输出（Output）——足够但不要太多；
  • 时长（Duration）——长时运行与后台进程；
  • 预算（Budgets）——何时停止重试并交还控制；
  • 隔离（Isolation）——代码在哪里运行、能触及什么。

【来源：原始课件 第 23 页】

5.3 另外五个常用工具

工具说明
A. 记忆与笔记把发现写进文件；计划能活过压缩（compaction）
B. 子智能体与委派探索只返回候选清单，而不是 40 次文件读取
C. 网页搜索与抓取先读已安装的源码，再查网络
D. 浏览器与视觉反馈对渲染结果截图并回喂给模型
E. 询问用户一个便宜的问题胜过自信的错误补丁

【来源：原始课件 第 24 页】

5.4 工具设计最佳实践

  • 少而正交的工具：重叠的工具会让模型在它们之间犹豫。
  • 专用而非通用：search_orders(customer_id) 胜过裸的 run_sql。
  • token 廉价的输出：截断、分页、摘要——工具设计就是上下文设计。
  • 能教人的错误：返回修复提示，而不只是「invalid argument」。
  • 默认幂等：尽可能让重试是安全的。

课堂问题「能不能只提供 shell 工具？」——课件给出了 SWE-agent 的实验结果：No specialized editor 10.3%、Shell only 11.0%、Full-file view 12.7%、Full interaction history 15.0%、Purpose-built SWE-agent 18.0%（GPT-4 上）。答案留待作业中自己体会。

【来源：原始课件 第 25–26 页】

6 从提示工程到上下文工程

6.1 术语的演进

【来源：原始课件 第 28 页】

6.2 提示工程的技术谱系

  • Zero-shot 零样本：只给指令。任务常见、格式能用话说清时用。
  • Few-shot 少样本：指令 + 几个示例。输出形状特殊或规则难以言传时用。
  • Role & persona 角色人格：给模型一个角色。语气或判断重要、受众特定时用。
  • Chain-of-thought 思维链：把推理步骤显式列出，答案放最后。任务真有步骤时用。
  • Tree-of-thoughts 思维树：分支、打分、剪枝。多条路径都合理且能廉价打分时用。
  • Self-consistency 自洽性：多次采样、多数投票。存在唯一正确答案且答错代价高时用。
  • Prompt chaining 提示链：一次调用一件事，验证过的交接。工作可分阶段时用。
  • Meta prompting 元提示：让模型自己改写 prompt。你有评测集、prompt 本身是要调的对象时用。

【来源：原始课件 第 29–37 页】

6.3 选择正确的技术

层次技术适用
从简单开始Zero-shot / Few-shot / Role & persona常见任务基线 / 特殊输出形状或隐性规则 / 语气或判断
加入推理Chain-of-thought / Tree-of-thought / Self-consistency多步推理 / 多路径打分 / 多次询问取多数
工程化系统Prompt chaining / Meta prompting可分阶段且可验证 / prompt 本身是要调的产物

课件提醒：有些技术「已经过期」——留待作业中自行发现。

【来源：原始课件 第 38–39 页】

6.4 设计提示的四个最佳实践

  • 先简单后迭代：需要时才加上下文。
  • 分区块：上下文、指令、工具、输出规格分开。指令、分隔符、数据——按此顺序。
  • 具体而简洁：花哨的措辞没有任何好处。
  • 把大任务拆成子任务：不要一开始就把复杂性堆满。

提示建议是与具体模型绑定的——换模型就要重新调。

【来源：原始课件 第 40 页】

7 上下文工程

定义（Karpathy） 上下文工程是「用恰到好处的信息填充上下文窗口，以支撑下一步操作」的精妙艺术与科学。（Context engineering is the delicate art and science of filling the context window with just the right information for the next step.）

【来源：原始课件 第 41 页】

7.1 上下文是有限资源

维度问题后果
Cost 成本每一步都重新发送整个窗口每一轮都要再付一次钱
Latency 延迟越大的 prompt，prefill 与 decode 越慢每一轮循环都更慢
Attention 注意力窗口越满，回忆越弱，中间部分被漏掉更多上下文 ≠ 更好答案

【来源：原始课件 第 42 页】

7.2 长度和位置都会损害准确率

两组实验结论：① 输入越长，准确率衰减（简单查找 73% → 带干扰项 46%）；② 答案在窗口中的位置也重要——在 20 篇文档中，答案位于第 1 位约 76%、第 5 位约 61%、第 10 位约 55%、第 15 位约 59%、第 20 位约 71%，中间位置最差。这就是「Lost in the Middle」与 Context Rot 现象。

来源：Chroma「Context Rot」；Liu et al., "Lost in the Middle," TACL 12 (2024)。

【来源：原始课件 第 43 页】

7.3 上下文窗口的解剖（单次调用的示意预算）

组成示意 token 预算
System prompt 系统提示~2K
Tool definitions 工具定义~6K
Retrieved context 检索到的上下文~25K
Message history（用户 + LLM + 工具结果）~8K
Project environment 项目环境~80K 且还在增长

课堂问题：上下文太大时该怎么办？（举手加分）

【来源：原始课件 第 44 页】

7.4 管理上下文窗口的四类手段

从预防性、无损 → 有损、不可逆，依次是：Admission（准入）→ Offloading（卸载）→ Transformation（转换）→ Compaction（压缩）。

手段含义
Admission 准入守卫什么进入窗口
Offloading 卸载需要时才加载，保持可检索而非常驻
Transformation 转换有选择地丢弃历史
Compaction 压缩用 LLM 做最后的手段

【来源：原始课件 第 45 页】

7.5 Admission：守住入口

  • 定向检索：查询要窄，取字段而非整篇文档。
  • 工具输出塑形：丢掉 DOM，只保留抽取结果。
  • 截断：只有在塑形不够时才限制大小。
  • 隔离：把原始载荷交给子智能体。

示例：原始 DOM 直通 = 48,000 tokens → 在入口塑形后只留价格与标题 = 900 tokens（小 98%，答案相同）。

【来源：原始课件 第 46 页】

7.6 Offloading：需要时才加载

  • 渐进式工具定义——只在需要时加载 schema；
  • 工具搜索——保留索引，按需取用；
  • 工具输出卸载——返回句柄（handle），按需加载；
  • 外部化任务清单——把计划放在磁盘上；
  • 持久记忆——把笔记写出去，只保留小索引。

示例：60 个 schema 常驻 = 42,000 tokens → 索引 + 3 个 schema = 3,100 tokens（小 93%，60 个工具仍全部可达）。

【来源：原始课件 第 47 页】

7.7 Transformation：有选择地丢弃历史

  • 去重（Deduplication）——只保留每个对象的最新状态；
  • 观察掩码（Observation masking）——剥离超过 N 步的工具结果；
  • 滑动窗口（Sliding window）——只保留最近的轮次与开头。

示例：保留每个结果 = 96,000 tokens → 只留最新状态 = 24,000 tokens（小 75%，没有任何内容被摘要）。

【来源：原始课件 第 48 页】

7.8 Compaction：把 LLM 作为最后手段

  • 滚动摘要：边走边总结旧的工具结果。
  • 完整摘要：到达上限时重写整段历史。
  • 自动记忆：把关键事实持久化到窗口之外。
警告 为输出预留空间（headroom）；保留系统前缀；压缩后重新注入关键事实。

【来源：原始课件 第 49 页】

7.9 上下文失效的五种方式

失效描述
Poisoning 投毒一个幻觉进入窗口，之后被当作事实引用
Distraction 分心历史增长到智能体开始模仿自己过去的动作
Confusion 混淆无关工具与文档把答案带偏
Clash 冲突新信息与旧信息矛盾，两者都未解决
Drift 漂移真正的目标被掩埋，换成附近的子目标
要点 给失效命名，修复方案就变得显而易见。（Name the failure and the fix becomes obvious.）参考：Breunig, "How Contexts Fail and How to Fix Them" (2025)。

【来源：原始课件 第 50 页】

7.10 智能体 = 模型 × 外壳

模型能力决定天花板（ceiling）；外壳决定实际的表现（realized performance）。

基准基础外壳改进外壳
