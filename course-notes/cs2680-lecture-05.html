3 八种多智能体架构

概览：① 主管—工人；② 层级；③ 流水线 / DAG；④ 黑板；⑤ 委员会；⑥ 市场；⑦ 集群；⑧ 动态拓扑。

【来源：原始课件 第 8 页】

3.1 主管—工人（Supervisor–worker）

一个智能体负责规划、委派与整合；工人只看到自己的子任务。示例：supervisor 下接 Researcher、Coder、Reviewer。最适合子任务独立、可并行的场景。

弱点 主管成为瓶颈：它要重读每个结果，上下文增长最快。任务=主管预先分解；控制=单一主管；通信=星形，经由主管。

【来源：原始课件 第 9 页】

3.2 层级智能体（Hierarchical）

把「主管—工人」递归应用：主管管理子主管。适合本身就分层分解的任务——存储、查询引擎、测试。示例（功能构建）：Feature manager → Backend lead / Frontend lead → API / Database / UI / E2E tests。

挑战 在哪里分解，以及多少上下文跨越每个边界？任务=每层再分解；控制=嵌套主管；通信=树形，仅父子之间。

【来源：原始课件 第 10 页】

3.3 流水线 / DAG（Pipeline / DAG）

固定阶段，每个边界有类型化契约（typed contract）。示例（发票处理）：OCR → 提取字段 → 匹配 PO → 审批 → 记入账本。是最容易调试的拓扑——错误能定位到某一阶段。

弱点 没有回头的路：第四阶段不能要求第一阶段提供更好的来源。「一条重试边胜过再加一个智能体。」任务=设计时固定阶段；控制=顺序本身；通信=阶段到阶段。

【来源：原始课件 第 11 页】

3.4 黑板与共享记忆（Blackboard）

智能体通过共享状态而非直接消息协调；工作区可以是数据库、向量库、文件系统、Git 仓库或任务图。示例：多个智能体共享一个 Git 仓库（task list、commits、history）。

优点：智能体可以加入或离开而无需重新接线；共享状态持久且可检查。挑战：一致性、并发控制、来源追溯（provenance）、版本管理、垃圾回收。任务=从共享状态涌现；控制=无中心；通信=经由工作区的间接通信。

【来源：原始课件 第 12 页】

3.5 委员会 / 辩论（Committee / debate）

智能体提出并讨论，然后由裁判或投票解决分歧。示例（作文评分）：Judge + Grader A + Grader B。能提高判断密集型任务的准确率。

失败模式 「没有独立性的共识」——相同的模型与上下文，同样的盲点（agreement without independence）。任务=同一任务并行重复；控制=裁判决定；通信=先同伴后裁判。

【来源：原始课件 第 13 页】

3.6 市场与拍卖（Market / auction）

智能体基于能力、成本与延迟对公布的任务出价。示例（GPU 作业路由）：A100 $0.20/ETA 3s、T4 $0.05/ETA 10s、H100 $0.40/ETA 1s ——「5 秒内最低价中标」，作业给 A100。工作落到最便宜且有能力的智能体，无需中央规划者。

弱点 出价是自报的，智能体可以通过夸大能力而中标。任务=公布后按出价认领；控制=拍卖方清算；通信=广播、出价回传。

【来源：原始课件 第 14 页】

3.7 集群（Swarm）

没有永久协调者，智能体直接协商、交换发现。示例：仓库机器人协商谁拣哪个订单。需要发现、寻址、同步、终止、信任等协议。

弱点 没有协调者瓶颈或单点故障；同伴进出工作继续。但通信复杂度 O(n²)，冲突解决困难，产品中很少使用。任务=局部协商；控制=无永久协调者；通信=全互联 O(n²)。

【来源：原始课件 第 15 页】

3.8 动态拓扑（Dynamic topology）

任务运行中可以添加、移除或重连智能体。示例：客服机器人在工单升级时才加入计费与日志智能体。容量随难度扩展，简单工单保持便宜。

弱点 每次运行形态都不同，失败难以复现。任务=工作变难时再分解；控制=随智能体加入而转移；通信=运行时动态。

【来源：原始课件 第 16 页】

3.9 真实系统是混合体

示例：Planner agent（主管）→ 动态任务 DAG，其下 Coder、Researcher、Tester、Reviewer 通过共享 Git（shared memory）协作，必要时重新规划（re-plan）。它结合了层级、共享记忆、流水线三种模式。

【来源：原始课件 第 17 页】

3.10 八种架构总览

类别架构核心思想最适合弱点
集中式主管—工人一个规划者，多个工人可分离的子任务规划者瓶颈
集中式层级主管的主管递归分解错误放大
集中式流水线 / DAG每阶段喂给下一阶段清晰的有序阶段错误传播
集中式市场 / 拍卖智能体为任务出价动态分配错误出价
去中心化黑板共享工作区单一共享工件陈旧状态
去中心化委员会 / 辩论先回答再调和判断类决策群体思维
去中心化集群直接对话，无控制器局部协商O(n²) 消息
混合动态拓扑随工作推进重连结构未知难以调试

【来源：原始课件 第 18 页】

4 协调：任务分解

复杂任务 → 子任务 1 / 2 / 3 → 合并结果。

【来源：原始课件 第 19 页】

4.1 分解的六个维度

维度说明
Data 数据每个智能体处理一部分文档或记录
Expertise 专长安全、性能、正确性、法律分析
Stage 阶段规划、实现、测试、审查
Hypothesis 假设智能体调查相互竞争的解释
Tool 工具网页、数据库、代码执行或内部文档
Authority 权限智能体在不同的管理域中行动

示例：一个 200 文件的 PR，先按数据（文件）分解，再按专长（安全、性能）分解。

【来源：原始课件 第 20 页】

4.2 创建子任务时要考虑的要素

  • 目标（Objective）、输入与相关上下文、边界与排除项、可用工具与权限、预期输出 schema、完成测试、预算与截止时间、依赖关系。
示例
较差的子任务「研究存储系统」
更好的子任务「找出 2026 年发表的存储相关论文；返回标题、日期、系统贡献、评测规模与一手来源 URL；排除数据库查询优化」

【来源：原始课件 第 21 页】

4.3 粒度权衡

任务太大 → 并行度低，工作仍是顺序的；任务太小 → 调度与通信开销占主导。公式：T_multi ≈ T_planning + T_critical path + T_communication + T_merge。只有当省下的顺序工作超过规划、通信与整合成本时，并行化才有帮助。

示例：把 20 个单行查找批量成 4 个子任务，使开销低于收益。

【来源：原始课件 第 22 页】

4.4 静态 vs 动态分解

类型说明示例
Static 静态执行前已知；可预测、易评估摘要每个上传的 PDF
Dynamic 动态智能体根据发现创建新任务死链触发一个查找任务
Recursive 递归工人本身也可以委派审查智能体为每个子领域派生一个子智能体
Opportunistic 机会式空闲智能体认领新出现的任务空闲智能体拾起下一份未标注文档
必须有护栏 分解需要派生限制、预算、深度限制与终止条件——否则委派会递归式爆炸（delegation explodes recursively）。

【来源：原始课件 第 23 页】

4.5 六种常见的分解失败

失败描述
01 Overlap 重叠两个智能体摘要同一篇论文
02 Gap 缺口「2020–2023」加「2025–2026」跳过了 2024
03 Hidden dependency 隐藏依赖定价需要尺寸，但尺寸只在运行时才发现
04 Unmergeable outputs 无法合并一个返回自由文本，另一个返回 JSON
05 Lost global context 丢失全局上下文每一节都没问题，但整篇报告自相矛盾
06 Straggler 落后者六个智能体 20 秒完成，一个耗时 4 分钟

【来源：原始课件 第 24–25 页】

5 通信

5.1 多智能体通信的四个维度

维度问题选项
Topology 拓扑谁能和谁说话？主管—工人、点对点；由架构决定
Medium 媒介信息如何交换？消息、共享记忆、文件、数据库
Format & Semantics 格式与语义消息如何构造、如何表达信息？delegate、report、ask、handoff、cancel
Channel 通道信息如何传递？p2p、广播、pub–sub、共享状态、请求—响应

【来源：原始课件 第 27 页】

5.2 通信媒介

媒介说明
消息传递 Message passing智能体通过队列或总线发送显式消息，如 coder 把结果发到 orchestrator 的收件箱
共享记忆 Shared memory一个进程内状态对象，所有智能体读写，如随工作完成更新的共享任务清单
文件与工件（含 DB）工作产品通过文件存储交接，如 researcher 写 notes.md，writer 打开它

【来源：原始课件 第 28 页】

5.3 通信通道

  • 直接点对点消息——规划者把任务规格交给 coder；
  • 广播——编排者告诉所有智能体构建失败；
  • 发布—订阅——智能体订阅「新工单」主题并响应；
  • 共享黑板——智能体读写同一份发现暂存区；
  • 请求—响应——智能体查询检索智能体并等待文档；
  • 工件传递——一个智能体写 report.md，下一个读取。

【来源：原始课件 第 29 页】

5.4 消息格式与语义

自然语言灵活但有歧义；结构化消息易校验但表达力弱。实用设计是两者结合：自然语言承载内容，结构化协议承载协调。

一个带语义的消息示例：{task_id, type: result, status: complete, claim, confidence, evidence[], artifact, requires_response}。运行时已知的操作：DELEGATE、QUERY、REPORT、HANDOFF、UPDATE、CANCEL、ACK、ERROR、COMPLETE。

关键原则 把控制与内容分离；按字段路由，而不是按散文路由（Route on the fields, not the prose）。这样运行时无需问 LLM「这条消息是什么意思」就能路由、重试与停止。

【来源：原始课件 第 30–31 页】

5.5 通信设计空间与经验法则

维度选项经验法则
拓扑主管—工人、点对点、mesh镜像任务的依赖关系
媒介消息、共享记忆、文件每条链路用一种媒介
通道p2p、广播、pub–sub、请求—响应仅当所有人都必须知道时才广播
格式自然语言 + 控制字段按字段路由，不按散文

每个选择都在延迟、上下文或可靠性之间取舍。

【来源：原始课件 第 32 页】

6 通信是一个艰难的分布式系统问题

示例：Agent A 告诉 Agent B「购买 8 个 GPU 实例」，网络超时无回应——B 到底执行了吗？重试还是放弃？至多一次还是至少一次？这里能做到恰好一次吗？用 task_id 做幂等键、补偿/回滚路径——以及，重复购买谁付钱？

【来源：原始课件 第 33 页】

6.1 分布式系统固有的难题

难题说明
部分失败 Partial failure你无法区分一个慢的智能体和一个死掉的智能体
并发与非确定性多台机器同时修改状态
复制状态的一致性一致性、可用性、分区、延迟之间的取舍
没有全局时钟不同机器上的时钟不一致
不可靠网络包延迟、丢失、重排、重复……
调试与可观测性大量请求、带时钟漂移的分布式日志

多智能体系统继承了这些常见的分布式系统问题。

【来源：原始课件 第 34 页】

6.2 多智能体运行时的额外挑战

  • 调度：谁接下来运行、运行多久。
  • 状态管理：检查点、记忆、来源追溯与版本管理。
  • 资源分配：模型、CPU 及其他共享资源。

请求流没有预定路径——系统无法预知谁需要运行、运行多久、每个智能体消耗多少资源。

【来源：原始课件 第 35 页】

6.3 黑盒 LLM 带来的更多挑战

类别问题
上下文信息丢失（摘要丢掉工人知道的细节）、上下文污染（重要的被埋没）、陈旧信息（X=5 后 B 仍按 X=3 行动）、信念冲突（A 说安全，B 说有漏洞）
协调与通信可观测性与失败诊断（为什么失败？）、所有权丢失（都以为对方负责）、通信循环（A 问 B，B 问 C，C 问 A）

【来源：原始课件 第 36 页】

7 A2A：智能体对智能体协议

A2A 让智能体之间能发现能力、发送消息/创建任务、获取进度更新、返回工件。示例：「分析 X 公司是否应把推理栈迁移到 GPU Y」——Research Agent 通过 Agent Card 发现同伴，Finance Agent 估算 GPU 成本，Search Agent 找基准数据，Coding Agent 跑基准。

【来源：原始课件 第 37 页】

7.1 A2A Agent Card

每个 A2A 服务器发布一张机器可读的卡片（GET /.well-known/agent-card.json）：name、description、skills、supportedInterfaces、capabilities（如 streaming）、securitySchemes。调用者由此得知：身份、能力、端点、能力特性（streaming/push）、认证方式。

【来源：原始课件 第 38 页】

7.2 A2A 的三个核心抽象

抽象说明示例
Message 消息客户端与智能体之间的一轮交互「订一张去波士顿的机票」
Task 任务带 ID 与生命周期的有状态工作单元task-42: working → completed
Artifact 工件任务产生的输出行程 PDF 与预订数据

消息启动任务，任务以工件返回其结果；后续追问加入同一任务：「哪天？」→「10 月 3 日」。

【来源：原始课件 第 39 页】

7.3 A2A 任务生命周期与长任务跟踪

状态：Submitted、Working、Input required、Auth required、Completed、Failed、Rejected、Canceled。任务可以暂停等待输入或认证，然后恢复。示例：「订机票」→ Input required「哪天？」→「10 月 3 日」→ Working。

跟踪方式说明适用
Polling 轮询客户端反复检查直到完成短作业
Streaming 流式流式传输实时更新交互式输出
Push notification 推送完成时触发 webhook数小时级作业
边界 A2A 标准化的是通信，而不是编排：委派、拆分与停止仍由外壳负责。

【来源：原始课件 第 40–41 页】

7.4 MCP 与 A2A 对比

维度MCPA2A
主要抽象能力 / 工具智能体 / 任务
关系智能体 → 服务智能体 → 智能体
发现tools、resources、prompts智能体能力（Agent Card）
工作单元一次工具调用长时运行任务
内部状态能力接口理想上不透明
类比设备 / API 接口服务到服务 RPC

「一个 A2A 远端智能体本身可以调用二十个 MCP 服务器。」MCP 标准化的是 tools、resources、prompts，一个客户端对接多个服务器，且由宿主（而非模型）决定暴露什么。

【来源：原始课件 第 42–43 页】

8 多智能体设计原则

  • 真的需要多智能体吗？单个智能体往往足够，多个智能体通常只增加开销与复杂性。
  • 确定拓扑：反映任务依赖，最小化通信。
  • 识别信息丢失点：把聚合节点视为细节会丢失的地方。
  • 识别故障 containment 边界：确保系统不会停摆。
警告 密集 mesh 很少是最佳默认。更多通信可能只增加上下文压力，而不增加有用信息。

【来源：原始课件 第 44 页】

Blackboard黑板通过共享工作区间接协调
