2 智能体记忆：概念与设计问题

2.1 上下文窗口之外的持久状态

智能体记忆 = 上下文窗口之外的持久状态。两类状态：上下文窗口是临时工作状态（temporary working state）；记忆存储是跨交互的持久状态（persistent state across interactions）。用户 → 智能体外壳（含 LLM 与记忆存储）。

【来源：原始课件 第 5 页】

2.2 记忆设计的七个问题

问题决策点
谁拥有记忆？归属 ownership
值得保留吗？WRITE OR SKIP —— 决定 write
应变成什么形式？ENCODE / ORGANIZE —— 格式 format
这个任务需要它吗？RETRIEVE —— 任务 task
能得出什么更一般的教训？REFLECT / GENERALIZE —— 教训 lesson
它还有效吗？KEEP / UPDATE / DELETE —— 状态 status
它应该放在哪里？STORE —— 后端 backend

3 记忆设计的逐项展开

3.1 决定：什么时候某件事应成为记忆

把每次交互都写下来会同时提高召回率与噪声。可选策略：显式用户请求、确定性规则（启发式）、小型分类器、定期 LLM 审阅——在「高召回（写每次交互）」到「高精度（选择性写入）」之间取舍。

【来源：原始课件 第 7 页】

3.2 如何组织记忆

组织方式示例特点
原始事件 / 情节 Raw episodes「我们把服务从 vLLM 迁到了 SGLang」高保真；大而冗余
非结构化摘要「Uses SGLang for model serving」紧凑；可能丢上下文
结构化状态{"serving_engine":"SGLang"}可查询；schema 形成约束
知识图谱Project → USES → SGLang关联实体，刻画随时间的变化

【来源：原始课件 第 8 页】

3.3 如何存储记忆

后端示例特点
纯文件CLAUDE.md、scratchpad易于检查、diff 与搜索
键值 / 关系数据库Redis、SQLite、Postgres JSONB精确查找、过滤与事务
向量库pgvector、Chroma、Pinecone精确或近似相似度搜索
图数据库Neo4j、FalkorDB（Graphiti）关系查询与多跳遍历

【来源：原始课件 第 9 页】

3.4 何时使用记忆

模式机制优点 / 缺点
Automatic 自动每一轮：search → LLM → add+ 可预测、简单；– 增加延迟与无关上下文
Runtime-controlled 运行时控制if memory_needed: search(); if memorable: add()+ 选择性、高效；– 需要规则或分类器
Model-controlled 模型控制search_memory() / add_memory() / update_memory() / forget_memory()+ 按需驱动，由 LLM 决定；– 可能漏掉有用的读或写

许多系统采用混合方式；读策略与写策略可以不同。

【来源：原始课件 第 10 页】

3.5 如何检索记忆

语义相关性只是检索信号之一。基础流水线：Query → Vector search → Top-k memories → Prompt（语义匹配）。此外还要考虑：

信号说明
Semantic match 语义匹配含义与查询匹配
Scope 范围同一用户、项目、实体或任务
Importance 重要性漏掉或包含它的代价
Validity 有效性在此任务、此时刻为真
Provenance 来源来源、置信度与证据

【来源：原始课件 第 11 页】

3.6 如何从观察中泛化

示例：用户先后问了 vLLM、SGLang、TRT-LLM、LLM scheduling → 经反思（reflection）得到假设「用户频繁关注 LLM 推理系统」，置信度：中等。何时进行整合（consolidation）？① 积累足够新证据后（如每 N 个事件或上下文填满）；② 事实冲突或重复时；③ 尽可能放在后台任务中。

【来源：原始课件 第 12 页】

3.7 遗忘是一等操作

  • 生命周期控制：标记无效（mark invalid）、永久擦除（erase permanently）、TTL 到期、建立分层并从活跃记忆中淘汰。
  • 为什么要遗忘：陈旧信息、错误或冲突信息、隐私与安全、存储与检索成本。

【来源：原始课件 第 13 页】

3.8 记忆需要有效时间与来源追溯

示例：2026 年 4 月「项目用 vLLM 服务模型」（superseded 被取代）；2026 年 6 月「项目用 SGLang 服务模型」（current 当前）。有效时间（valid time）指哪个事实在何时适用；来源追溯（provenance）指事实从何而来。知识图谱边 Project → SERVES_WITH → SGLang，标注 source: Episode 28。

【来源：原始课件 第 14 页】

3.9 谁拥有记忆

模式说明
Agent-owned 智能体自有外壳中的文件：CLAUDE.md、agent scratchpad、任务笔记；外壳把记忆持久化到磁盘
Dedicated memory system 专用记忆系统智能体调用的服务：Mem0、Graphiti、supermemory；记忆是一种 API，跨智能体与会话共享

【来源：原始课件 第 15 页】

3.10 三种专用记忆系统

系统类型输入 / 检索
Mem0以事实为中心（fact-centric）输入：按用户/智能体/运行划分的消息；检索：带过滤的向量搜索，可选图记忆。如「Uses SGLang for model serving」
Graphiti时序知识图谱输入：产生实体与时间感知事实的情节；检索：混合语义、关键词与图搜索。如 uses → SGLang，valid Apr 2026 → present
supermemory画像 / 记忆 / 文档维护用户画像、记忆与文档；输入：链接到来源与时间的对话；检索：画像、记忆与文档搜索

【来源：原始课件 第 16 页】

3.11 智能体记忆设计清单

阶段要问的问题
Observe 观察（原始材料的获取）
Select 选择这值得记住吗？
Encode / organize 编码组织什么表示能保留所需含义？
Store 存储应该放在哪里？文件还是数据库？
Retrieve 检索什么对当前任务有用？
Reflect / consolidate 反思整合这是更新还是与旧记忆矛盾？
Forget 遗忘信息何时变得陈旧或无关？
要点 每一阶段都是一个策略决定（Each stage is a policy decision）。

【来源：原始课件 第 17 页】

3.12 记忆的失败模式

失败描述
Retrieval miss 检索遗漏相关记忆存在但没被找到
Context pollution 上下文污染太多无关记忆进入上下文
Memory hallucination 记忆幻觉推断被当作事实存下来：「在哈佛学习」变成「哈佛访问学生」
Staleness 陈旧旧事实覆盖了新信息
Isolation failure 隔离失败记忆跨越了用户边界
Overgeneralization 过度泛化一个事件变成持久偏好
Persistent prompt injection 持久提示注入不可信内容后来作为指令返回
Unbounded growth 无界增长规模随生命周期增长，检索成本与质量下降

4 智能体可靠性

4.1 为什么可靠性是个问题：错误会复合

运行只有在每一步都成功时才成功；错误传播让真实运行比理论估计更糟。假设每步独立成功率 95%，运行无错的概率随步数衰减：1 步 95%、5 步 77%、10 步 60%、20 步 36%、50 步 8%（约 1/13）。

关键 50 步的运行只有约 1/13 能无错完成——长轨迹智能体的可靠性是首位问题。

【来源：原始课件 第 22 页】

4.2 故障从哪里来：五层

故障来源核心问题类型
User / task spec 用户/任务规格目标是否明确无歧义？specification failure 规格失败
Agent harness 智能体外壳上下文、循环、调度harness failure 外壳失败
LLM推理与规划model failure 模型失败
Tool layer 工具层shell、浏览器、APItool failure 工具失败
Environment 环境仓库、OS、网页、服务environment failure 环境失败

【来源：原始课件 第 24 页】

4.3 任务规格失败

失败规格说智能体做了修复
目标含糊「修复登录 bug」修了三个中的一个指明文件、症状与复现
代理目标「让测试通过」删掉了失败的测试禁止改测试；审查 diff
未言明的约束「加速搜索」破坏了公开 API声明什么不能变
没有完成定义「清理解析器」无限重构停不下来给退出测试与停止规则
目标冲突「最小 diff，覆盖所有边界」悄悄丢弃边界情况显式排出目标优先级

【来源：原始课件 第 25 页】

4.4 外壳失败

失败外壳做了影响修复
上下文截断错误裁掉最旧的轮次忘了「保留 API」规则把关键规则固定在窗口之外
记忆错误把陈旧笔记当事实编辑了已移动的文件给记忆标日期；使用前复查
状态损坏错误保留了半应用的编辑后续步骤建立在损坏文件上检查点；回滚失败步骤
控制循环错误没设步数或成本预算200 步无进展限制步数、成本与时间
阻塞式 fan-out等待每个子智能体一个慢子进程拖垮运行设置超时；使用部分结果

【来源：原始课件 第 26 页】

4.5 模型失败

失败模型推理 / 智能体行为修复
幻觉「requests.fetch() 存在」→ 调用不存在的函数对照真实文档检查调用
违反指令「速度比 API 重要」→ 改了要求保留的签名重述约束；检查 diff
错误推理「超时意味着网络断了」→ 给死锁加重试修复前先验证假设
推理—行动不匹配「我只碰 parser.py」→ 重写了另外三个文件把每个动作与计划比对
未经验证的成功「测试现在应该过了」→ 宣称完成但没运行要求测试输出作为证据
长时程退化「配置还需修」→ 撤销了第 12 步自己的修复重读状态；拆成短任务

【来源：原始课件 第 27 页】

4.6 工具失败

失败工具返回 / 智能体行为修复
输出截断日志前 100 行 → 漏掉第 4000 行的错误错误优先返回；允许分页
静默失败exit 0、空结果 → 以为没有匹配区分「空」与「失败」
schema 含糊没有时区的日期 → 任务排错 8 小时使用类型化、明确的 schema
不稳定调用第一次尝试超时 → 宣称服务宕机先带退避重试再下判断
误导性错误拼写错误却报「Permission denied」→ 用 sudo 重试返回精确、可行动的错误

【来源：原始课件 第 28 页】

4.7 环境失败

失败环境状况 / 智能体行为修复
陈旧状态昨天缓存的构建 → 在旧代码上通过测试从干净缓存全新构建
版本不匹配Python 3.8 而非 3.12 → 交付崩溃代码在 lockfile 中固定版本
随机失败任务成功依赖环境 → 因闰年失败重跑失败；隔离不稳定项（quarantine flakes）
网页改版结账页重新设计 → 点错按钮行动前重新读取页面
速率限制50 次调用后 HTTP 429 → 迁移中途停止限流；对长任务设检查点

【来源：原始课件 第 29 页】

4.8 面向失败的设计

层面策略具体做法
任务规格把「完成」写成测试预先写验收测试；列出什么不能变
智能体外壳约束每一次运行步数、成本、时间上限；检查点与回滚
模型要求证据每个主张都要证明；验证；使用更强的模型
工具响亮地失败（fail loudly）类型化 schema；错误与空结果分开
环境固定并隔离全新、固定版本的沙箱；判断前先重试不稳定项

「我们对大规模智能体尚无充分理解，形式化的最佳实践也很少。」
