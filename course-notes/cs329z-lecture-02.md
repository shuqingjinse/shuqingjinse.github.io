## 1. 为什么构建者需要理解模型 {#perspective}

CS329Z 主要工作在 LLM 应用与系统层，而非要求每个学习者从头训练基础模型。但底层设计仍会影响应用：模型怎样生成、如何利用上下文、哪些环节贵、怎样训练得来，都会改变智能体的能力边界。

本讲目标是把内部机制转成工程判断。例如，长上下文能力不足时，不能只改一句「请认真阅读」；工具参数不可靠时，也不能仅依靠更长的文字描述。

| 模型层问题 | 智能体层的影响 |
| --- | --- |
| 解码是否随机 | 动作稳定性、多样性与复现实验 |
| 注意力怎样保存历史 | 长任务的信息利用与内存成本 |
| 训练数据和目标是什么 | 指令遵循、工具使用与任务适配 |
| 推理在哪个阶段耗时 | 交互延迟、调用预算与吞吐 |
| 输出怎样受约束 | 组件能否安全解析并继续执行 |

**课件依据：第 2—5 页。**

## 2. 语言模型是序列概率模型 {#probability}

语言模型为 token 序列分配概率。对序列 $$x_1,\ldots,x_T$$，自回归分解是：

$$
P(x_1,\ldots,x_T)=\prod_{t=1}^{T}P(x_t\mid x_{<t}).
$$

给定前文，模型产生下一个 token 的条件分布；选择一个 token 后，再把它加入前缀继续生成。Token 是分词器的单位，可以是词、词片段、标点或字符片段，并非总与一个自然语言单词对应。

序列概率是许多小数的乘积，可能非常小，因此实现中常累加对数概率：

$$
\log P(x_{1:T})=\sum_{t=1}^{T}\log P(x_t\mid x_{<t}).
$$

语言模型属于生成模型，能够从学到的分布中采样。式子里出现条件概率，不代表它自动变成判别模型；要看建模的对象，而不只是是否写了条件符号。

**课件依据：第 6—19、23 页。**

对构建者而言，要分清「模型给某个序列较高概率」与「该序列是正确、最新、获准执行的」。概率分布描述生成倾向，不直接完成事实核验或授权判断。

## 3. 解码策略与温度 {#decoding}

模型给出分布之后，还需要解码算法决定输出。

| 策略 | 怎样选下一个 token | 取舍 |
| --- | --- | --- |
| Greedy 贪心 | 选择当前概率最大的候选 | 简单，但局部最优不保证整段最好 |
| Top-k | 只在概率最高的 k 个候选中采样 | 候选数固定，不能自动适应分布形状 |
| Top-p / nucleus | 取累计概率达到阈值的高概率候选集合再采样 | 候选数量可随分布变化 |
| Beam search | 同时保留多条高分候选序列 | 计算与内存开销增加，分数不等于任务正确性 |

课件讨论数学、代码与创意写作的差异。低温常用于降低随机性，但复杂推理也可能从多样候选中受益，不能给所有代码任务固定一种最优设置。

### 温度实际缩放什么

设模型在 softmax 之前的分数为 logits $$z_i$$，常见温度采样是：

$$
P_T(i)=\frac{\exp(z_i/T)}{\sum_j\exp(z_j/T)},\qquad T>0.
$$

等价地，可对原概率做 $$p_i^{1/T}$$ 后归一化。较低温度使分布更集中，较高温度通常增加多样性。

**技术澄清：**课件第 20 页用「除以温度再归一化」作直觉说明；实际应缩放 logits，或对概率取上述幂次。若把所有概率直接除以同一个常数后再归一化，分布不会改变。

**课件依据：第 18—22 页。**

评估两种智能体设计时，应记录解码设置。一次低温生成与多次高温采样选最优，并不是相同预算下的公平比较；即使采用贪心，也不宜对服务端实现作绝对确定性的承诺。

## 4. Decoder-only Transformer {#transformer}

课件从 N-gram、神经语言模型、RNN 与 LSTM 讲到 Transformer，再逐步绘制现代 decoder-only 模型。几十页动画图可以合并成下面的主线：

~~~text
token IDs
  → 词嵌入与位置信息
  → 多层 Transformer block
      ├─ 归一化
      ├─ 因果自注意力
      ├─ 残差连接
      └─ 前馈网络等计算
  → 输出投影（LM head）
  → logits
  → 解码得到下一 token
~~~

不同模型的归一化、位置编码和层结构并不完全一样，这张图用于理解课件中的基本骨架。

### Query、Key、Value

把输入表示记为 $$X$$，经不同权重投影得到：

$$
Q=XW_Q,\qquad K=XW_K,\qquad V=XW_V.
$$

一个注意力头的常见形式是：

$$
\operatorname{Attention}(Q,K,V)
=\operatorname{softmax}
\left(\frac{QK^\top}{\sqrt{d_k}}+M\right)V.
$$

$$QK^\top$$ 给出位置之间的匹配分数，缩放帮助控制数值范围，$$M$$ 是因果 mask：生成当前位置时，不能查看训练序列中的未来答案。注意力权重再对 $$V$$ 做加权组合。

多头注意力以不同投影学习不同关系，将结果组合并投影回模型维度。残差连接保留并传递原表示，前馈网络进一步变换每个位置的表示。

**课件依据：第 24—60 页；公式按标准记法重写。**

训练时已知整段序列，可以并行计算多个位置的监督信号，因果 mask 防止偷看；生成时未来 token 尚不存在，仍要逐步选择。Transformer 易于并行训练，不等于生成全部 token 时没有顺序依赖。

## 5. 全注意力、线性注意力与混合架构 {#attention}

### 全注意力的优势与代价

在固定模型宽度下，对长度 n 的序列，朴素全注意力涉及约 n² 规模的位置匹配。历史越长，prefill 的计算和注意力相关处理就越昂贵。高效实现可以减少中间存储等开销，但不能据此认为历史交互完全免费。

全注意力的优势是，当前位置可以通过注意力直接访问之前的各位置表示。它仍可能漏用资料，但不需要先把全部历史压成一个固定大小的状态。

**课件依据：第 61—62、87 页。**

### 线性注意力：把历史压进状态

课件用去掉 softmax、改变矩阵乘法结合顺序，建立线性注意力直觉。若仅看一个省略归一化的示意式：

$$
(QK^\top)V=Q(K^\top V),
$$

就能先聚合历史，再回答当前查询。对因果序列，一个简化状态递推是：

$$
S_t=S_{t-1}+k_tv_t^\top,\qquad o_t=q_t^\top S_t.
$$

**这里是教学示意，不是与 softmax 注意力完全等价的替换。**实际线性注意力可能使用特征映射、归一化、门控、衰减或更复杂的状态更新。课件后续图展示的清除与更新，也是在说明如何管理压缩状态。

| 维度 | 全 softmax 注意力 | 线性 / 递归状态思路 |
| --- | --- | --- |
| 历史表示 | 保留可访问的逐 token KV | 将历史汇入状态 |
| 序列处理成本 | 朴素总注意力计算随 n² 增长 | 固定状态维度下可随 n 线性增长 |
| 推理历史存储 | KV 随历史长度增长 | 某些设计可用固定大小递归状态 |
| 取舍 | 长历史的计算与存储昂贵 | 压缩可能损失细节检索能力 |

**课件依据：第 63—87 页；递推式为补充说明。**

混合架构把不同注意力或状态层组合，尝试在精细访问历史与处理效率之间取舍。不能只看模型宣称的最大上下文长度，还应测试它在自己的长文检索、跨步骤决策中是否有效。

上下文能力受到位置表示、训练长度与数据、架构和部署资源共同影响。名义上能接收很长文本，不代表能准确使用所有位置，也不意味着超出训练长度就必然立即失效。

**课件依据：第 83—91 页；上下文能力边界为技术澄清。**

## 6. 从预训练到智能体专用训练 {#training}

### 监督目标：让实际 token 的概率提高

对目标 token，常见训练损失是负对数概率；整段训练可累加或平均：

$$
\mathcal L=-\sum_t\log P_\theta(x_t\mid x_{<t}).
$$

预测正确 token 的概率越低，损失越大。交叉熵用真实目标作为监督，通过梯度更新参数。

**数值说明：**课件第 99 页对 0.0124 给出约 1.907，这对应以 10 为底的对数；若按常见实现采用自然对数，则 $$-\ln(0.0124)\approx4.390$$。两者相差常数比例，本笔记公式统一采用自然对数。

**课件依据：第 92—100 页。**

### 不同训练阶段改变什么

| 阶段 | 主要关注 | 对智能体的意义 |
| --- | --- | --- |
| 预训练 | 大规模数据上的通用模式 | 建立语言、知识和代码等基础能力 |
| Midtraining 中期训练 | 调整数据混合，强化目标领域 | 更关注代码、数学或特定分布 |
| 指令微调 | 高质量输入—回答或任务示范 | 学习指令、交互和输出习惯 |
| 偏好学习 | 人或模型的比较反馈 | 改善行为倾向，也可能产生迎合等偏差 |
| 可验证奖励 RL | 根据答案、测试、状态等反馈更新 | 适合有可信验证器的任务 |
| 智能体专用训练 | 多步工具轨迹、软件任务等数据 | 学习行动、观察与修复的组合行为 |

这些是常见组织方式，不是所有模型必须依次经历的固定工序。阶段名称与边界也会随训练方案变化。

预训练的数据工程包括提取正文、语言识别、去重、规则与质量过滤、数据混合。收集更多文本并不自动改善目标能力；数据分布决定了模型会反复见到什么。

**课件依据：第 101—113 页。**

人类反馈也会有噪声、标准差异与采集伦理问题。若标注总偏好自信、顺从或冗长，优化可能强化这些表面特征，而非真实正确性。

RLVR 可以使用单元测试、形式证明、答案匹配或环境状态作为奖励。但验证器有漏洞时，模型可能优化「拿分」而非完成任务。课件再用 SWE-smith 说明智能体数据与任务环境的重要性：专门的多步能力，需要与实际任务有关的训练信号。

**课件依据：第 114—118 页。**想深入 SFT、DPO、GRPO，可结合本站的[后训练课程笔记]({{ '/course-notes/post-training/' | relative_url }})阅读。

## 7. Prefill、Decode 与 KV Cache {#inference}

### 为什么首个 token 和后续 token 的等待不同

**Prefill（预填充）**处理已知输入前缀，形成用于后续生成的状态；**Decode（解码）**在已有前缀上逐步生成新 token。

| 阶段 | 主要工作 | 用户更直接感受到的指标 |
| --- | --- | --- |
| Prefill | 处理输入上下文 | 首 token 延迟（TTFT） |
| Decode | 一步步生成输出 | 每输出 token 时间（TPOT） |

实际 TTFT 还包括排队、网络和服务调度。长输入可能拖慢开始回答，长输出则会拉长后续生成时间；两个问题对应的优化方向不完全一样。

课件用 GPU 与 roofline 模型解释计算和内存带宽的取舍：prefill 往往有较多可并行计算，较低批量的 decode 常更受内存访问影响。真实瓶颈仍取决于模型、批量、硬件与服务配置。

**课件依据：第 119—123、134—135 页。**

### KV Cache 缓存的是中间状态

因果生成中，旧 token 对应的 Key、Value 可以保留，新 token 不必每次重新计算全部历史位置的 K、V。新查询仍需与相关历史交互，也仍有生成与前馈计算。

因此 KV Cache：

- 节省重复计算，但不等于缓存了一份答案。
- 对全注意力模型通常随历史长度增长，占用内存。
- 依赖模型与前缀状态；更改已缓存的历史会使后续状态无法直接复用。

课件动画中为了突出下一步计算而清除部分画面，不能理解为系统自动知道并删掉所有「不重要」历史。实际保留与淘汰策略需要单独设计。

**课件依据：第 124—133 页；缓存边界为技术澄清。**

## 8. 推测解码与推理时扩展 {#scaling}

### Speculative decoding：便宜草拟，目标模型验证

一个较便宜的草拟过程先提出若干 token，再由目标模型批量验证，接受符合条件的部分，修正不合适的部分。若预测容易且接受率高，就可能减少目标模型顺序解码的开销。

这不是无条件让小模型替大模型回答。具有严格采样校正的经典方法旨在保留目标分布，具体实现与接受规则仍然重要；难预测任务、较低接受率或不合适的服务负载下，收益也会下降。

**课件依据：第 136—137 页。**

### Test-time scaling：把更多计算用在一次任务上

课件讨论三类方法：

| 方式 | 怎样增加计算 | 需要的条件 |
| --- | --- | --- |
| 更长的内部推理 | 分解、检查和修正 | 模型能有效利用增加的预算 |
| 重复采样 | 生成多条候选再选择 | 有合适的评分或验证方法 |
| 自洽性聚合 | 没有直接验证器时比较答案一致性 | 候选多样，且多数不共享同类错误 |

模型为什么会按不同推理预算工作，可能与训练时的预算奖励、不同强度的示范或蒸馏有关，不只是提示词加一句「再想久一点」。

**课件依据：第 138—148 页。**

更多 token 不保证更好。对智能体而言，预算应该看完整任务：更长思考、多次采样、重复调用和工具时间都会累积。评估时要说明采样数与挑选方法，不能只报告最幸运的一次成功。

## 9. 结构化输入输出与约束解码 {#structured}

复合系统的组件需要共同的通信契约。例如一个工具选择器应输出工具名和参数，而不是任意散文；一个信息抽取器需要按约定返回字段。

**Constrained decoding（约束解码）**在生成时限制允许的后续 token，使输出满足某种语法或结构。课件用有限状态机与 SGLang 的例子说明，而不只是事后要求「请输出 JSON」。

**课件依据：第 151—154 页。**

~~~json
{
  "tool": "read_file",
  "arguments": {"path": "notes.md"}
}
~~~

这是本篇自编格式。结构正确仍有三层需要检查：

| 检查 | 能发现什么 |
| --- | --- |
| 语法和类型 | JSON 是否可解析，字段是否齐全 |
| 语义和资源 | 路径是否存在，参数是否满足真实任务 |
| 权限和动作 | 是否允许读取，是否会越过范围 |

课件还展示 **DSPy signature**：用输入字段、输出字段、类型和任务描述声明模块契约，再由适配器组织实际提示与解析。声明类型有利于组合，不表示每个适配器都自动获得严格的 token 级约束。

如果任务只是有限标签分类，分类头或受限决策模型也可能比开放式生成更合适。选择输出机制应服务真实决策空间，而不是所有环节都生成长文本。

**课件依据：第 155—159 页；结构与授权分层为补充。**

## 10. 上下文工程：选择、顺序与压缩 {#context}

提示工程关注怎样写指令；**上下文工程（context engineering）**还要决定模型此刻能看到哪些资料、历史、工具定义和状态，以及它们怎样组织。

课件列出的输入包括系统提示、消息历史、记忆、工具结果和附件。全部塞入可能增加成本和干扰，形成 context rot：材料虽然能放进窗口，任务表现却下降。

**课件依据：第 160—165 页。**

### 控制膨胀，按需检索

工具越多，定义和选择空间也越大。课件用少量通用工具的 harness 作例子，说明工具数量不是能力的简单计数；需要具体测试描述、粒度和权限。

对文件与记忆，可以先建立索引，再按任务取回最相关部分，保持来源可回查。检索失败时要显式处理，不能靠模型补全缺失证据。

**课件依据：第 166—167 页。**

### 追加历史与缓存复用

对标准因果 Transformer，追加新内容可以保留原前缀状态；在前面插入或改写内容，会改变后续位置、注意力和中间状态。若服务支持前缀缓存，稳定的公共前缀通常更容易复用。

这不是要求永远不清理历史。无关内容带来的准确率与延迟代价，可能大于缓存收益；应同时看任务效果和实际成本。

**课件依据：第 168—170 页。**

### Compaction：压缩时保留什么

压缩是一次信息取舍。保留过多，很快又要压缩；删掉过多，则可能丢失完成任务所需的约束或事实。

以下是补充的压缩清单：

| 应保留 | 为什么 |
| --- | --- |
| 目标、完成标准与权限 | 防止任务和边界漂移 |
| 已确认的事实及来源 | 让结论可核对 |
| 关键决定与未解决问题 | 避免重新争论或重复失败 |
| 当前产物路径与状态 | 让下一步能继续 |
| 必要失败经验 | 避免机械重试 |

完整日志可以外存，但摘要不能取代需要精确内容时的原始文件。压缩效果需要同一组评估任务验证，而不是只比较摘要有多短。

**课件依据：第 170—171 页；清单为补充实践。**

## 11. 另一种思路：递归语言模型 {#recursive}

课件最后介绍 **Recursive Language Models（RLMs）**：把很长的材料作为外部执行环境中的数据，由模型通过程序查看、分割、搜索，并按需对子问题调用语言模型，最后组合结果。

它与「一次把整本书塞进提示」不同：大输入可以放在环境里，模型逐步选择要看什么。递归子调用处理局部问题，但仍需要管理结果、出处、调用预算与执行环境。

~~~text
外部材料
   ↓
程序读取 / 切分 / 搜索
   ↓
对子问题调用模型
   ↓
整合结果并核对覆盖范围
~~~

这是对课件图的文字重绘。外部存储不代表无限理解，也不自动消除漏读、错误聚合或递归开销。运行模型生成的代码仍需要受控环境。

**课件依据：第 172—173 页。**

## 12. 构建清单、术语与自测 {#practice}

本讲各项内部机制，最后都落到智能体设计的几个问题：

| 设计问题 | 可以怎样验证 |
| --- | --- |
| 需要多少输出多样性？ | 固定预算，对比不同解码下的任务通过率 |
| 长历史真的被用到了吗？ | 改变证据位置、加入干扰并检查引用 |
| 慢在输入还是输出？ | 分开记录 TTFT、生成长度与 TPOT |
| 工具输出是否可靠？ | 同时验证结构、参数与权限 |
| 压缩是否丢信息？ | 用需要早期约束的留出任务测试 |
| 更多推理是否值得？ | 同时报告成功率、总时间与费用 |

**自编练习：**对同一份公开资料做一个固定流程助手，分别测试「全部材料」「检索片段」「压缩后的交接摘要」三种上下文。保持问题和输出要求一致，记录答案正确性、来源覆盖、耗时与 token 用量。

术语速查：**logits** 是归一化前分数；**temperature** 调整采样分布；**causal mask** 限制查看未来位置；**prefill** 处理输入前缀；**decode** 逐步生成；**KV Cache** 复用历史 K/V；**signature** 声明模块字段与任务；**compaction** 压缩当前上下文。

<details><summary>为什么把所有概率除以温度再归一化不起作用？</summary><p>共同的除数在归一化时相消。温度采样缩放的是 logits，或等价地对概率取 1/T 次幂后归一化。</p></details>

<details><summary>全注意力与线性注意力的选择，为什么会影响智能体？</summary><p>智能体可能积累很长的历史。逐 token 访问与压缩状态在精细检索、计算和内存上有不同取舍，必须在真实长任务上比较。</p></details>

<details><summary>KV Cache 是否让历史 token 完全没有成本？</summary><p>没有。它避免部分重复计算，但缓存占内存，新 token 仍需计算并与历史状态交互。具体开销还受架构与服务设置影响。</p></details>

<details><summary>结构化输出保证的是正确答案吗？</summary><p>主要约束输出形式和部分类型。内容是否真实、参数是否合理、动作是否获准，还需要独立检查。</p></details>

<details><summary>生成更长的计划，总能提高智能体可靠性吗？</summary><p>不能。计划可能基于错误前提，长历史也可能增加干扰。更可靠的依据是观察反馈、可验证的中间结果和任务级评估。</p></details>
