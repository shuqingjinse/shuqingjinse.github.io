## 1. 为什么要从零构建 {#purpose}

调用 API、下载模型和使用训练框架，可以让人很快得到结果，但也可能掩盖结果背后的条件：数据怎样处理、参数如何更新、显存消耗在哪里，以及哪些实验结论只能在特定规模成立。

CS336 用亲手实现来建立理解。它希望培养三种能力：

| 能力 | 学习时应该追问 |
| --- | --- |
| 工作机制 | 每个组件接收什么、输出什么，为什么这样计算？ |
| 资源意识 | 同样预算下，怎样减少无效计算和数据搬运？ |
| 实验直觉 | 哪些数据、结构和超参数在当前规模有效？证据是什么？ |

前两项较容易迁移到更大模型；第三项需要谨慎。小模型的性能瓶颈、注意力与 MLP 的计算占比，甚至某个结构改动的收益，都未必在大规模保持不变。

课程对规模化的理解也包含算法效率：能有效利用更多资源的方法才有价值。固定预算下，数据筛选、计算组织和模型结构共同决定结果。这里不把「效果 = 效率 × 资源」当作可直接计算的物理公式，而把它作为研究取向。

**讲义依据：`welcome`、`why_this_course_exists`、`current_lm_landscape`。**原讲义还回顾了 n-gram、神经语言模型、注意力、Transformer、预训练与智能体的发展；这一历史线索帮助理解任务形态在变化，而训练、计算与数据这些基础问题仍然存在。

## 2. 全课地图：资源效率贯穿始终 {#roadmap}

原课把学习任务分成五块。第一讲介绍它们的关系，随后才深入分词；下面的内容是全课预览，不表示本讲已经讲完全部技术。

| 模块 | 要做的事 | 从效率角度看 |
| --- | --- | --- |
| 基础 | 分词、Transformer、损失、优化器与训练循环 | 在表达能力、稳定性与计算成本间平衡 |
| 系统 | GPU kernel、并行训练、推理 | 尽量复用数据，减少内存和设备间搬运 |
| 扩展规律 | 用较小实验预测大规模配置 | 避免每次调参都付出完整训练成本 |
| 数据 | 评估、提取、过滤、去重、混合与合成 | 把训练预算用在更有价值的样本上 |
| 对齐 | 从偏好、验证器或其他奖励改进模型 | 同时管理训练稳定性和生成样本的成本 |

例如，分词会改变序列长度，从而影响注意力成本；数据去重减少重复更新；并行方案决定显存能否容纳模型，也会引入通信成本。它们不是互不相关的独立技巧。

扩展规律的关键是建立可检验的预测。把较小实验拟合出的关系外推到大模型，需要相容的训练方案和验证；某个经验比例也会随数据分布、推理成本和目标而变化。

对齐则把「预测已有 token」扩展到「生成候选、评价候选、更新模型」。这部分与本站[后训练课程](../post-training/)衔接，但 CS336 还要求理解支撑训练和采样的系统。

**讲义依据：`course_syllabus`、`basics`、`systems`、`scaling_laws`、`data`、`alignment`。**课程实践量较大，建议先自行推导，再实现和测量；作业细节与时间安排以官网为准。

## 3. 语言模型与分词器的接口 {#interface}

原始输入通常是字符串，神经网络处理的却是整数索引序列。分词器负责建立二者之间的转换：

~~~text
文本 → encode → token ID 序列 → 语言模型
文本 ← decode ← token ID 序列 ← 生成结果
~~~

两个基础接口是 `encode(text) -> list[int]` 和 `decode(ids) -> str`。词表则说明每个合法 ID 代表什么。**ID 是索引，不代表词义的数值大小**；例如 ID 500 不比 ID 5「更有意义」。

对于本讲使用的、无损且不额外归一化的分词方式，希望满足：

~~~python
assert decode(encode(text)) == text
~~~

这检验的是编码后能否还原原文，不要求把任意 ID 序列解码再编码后都得到同一串 ID。某些生产分词器还包含归一化或特殊 token 策略，需要另看其约定。

**补充理解：语言模型到底预测什么？**若分词结果为 $$x_1,\ldots,x_T$$，自回归模型用条件概率分解序列概率：

$$
p_\theta(x_1,\ldots,x_T)=\prod_{t=1}^{T}p_\theta(x_t\mid x_{<t}).
$$

给定前面的 ID，模型对词表中的下一个 ID 输出概率分布。分词器决定预测单位，模型参数决定这些单位在上下文中的概率。训练分词器与训练语言模型是两个阶段，优化对象不同。

**讲义依据：`Tokenizer`、`intro_to_tokenization`、`tokenization_examples`；概率公式为补充。**

## 4. 字符、码点与 UTF-8 字节 {#unicode}

「一个字」「一个字符」「一个字节」「一个 token」不是同一个单位。先把 Unicode 与字节编码分开，才能理解 byte-level BPE。

| 层次 | 含义 | 例子 |
| --- | --- | --- |
| Unicode 码点 | 字符编码空间中的整数位置 | `ord("a")` 为 97 |
| Python 字符串 | 一串 Unicode 码点 | `"中"` 的字符串长度为 1 |
| UTF-8 编码 | 把码点编码成字节序列 | `"中"` 编为 3 个字节 |
| token | 分词器选定的建模单位 | 可以覆盖多个字节，也可能只是字符的一部分 |

**补充算例：**

~~~python
text = "a中🌍"
print([ord(c) for c in text])
# [97, 20013, 127757]

raw = text.encode("utf-8")
print(list(raw))
# [97, 228, 184, 173, 240, 159, 140, 141]

assert len(text) == 3
assert len(raw) == 8
assert raw.decode("utf-8") == text
~~~

`a` 使用 1 个字节，`中` 使用 3 个字节，`🌍` 使用 4 个字节。不能根据字符串的字符数直接推断字节数，也不能据此推断某个模型的 token 数。

**补充边界：**人眼看到的一个字符还可能由多个码点组成，例如某些组合音标或 emoji 序列。因此 `len(text)` 也不总等于屏幕上看到的字符个数。

一个 token 对应的字节片段未必能单独解码为完整 Unicode 字符。对字节级分词器，正确的解码思路是先把全部 token 的字节拼起来，再执行 UTF-8 解码。对原文的完整往返可以成立，但模型任意生成的字节序列未必是合法 UTF-8；实际系统需要规定错误处理方式。

**讲义依据：`CharacterTokenizer`、`ByteTokenizer`、`character_tokenizer`、`byte_tokenizer`；组合字符与解码边界为补充。**

## 5. 字符、字节与词级分词 {#alternatives}

三种直观方案各有代价。这里的字符方案按码点处理，不涉及人眼字符的复杂切分。

| 方案 | 优点 | 局限 |
| --- | --- | --- |
| 字符级 | 接口简单，容易理解和还原 | 码点空间大，罕见字符难学；序列仍可能很长 |
| 字节级 | 基础词表只有 256 项，可覆盖任意 UTF-8 文本 | 一个字节一个 token，常导致较长序列 |
| 词级 | 常见词可以整体表示，序列较短 | 词表大、长尾多，新词与变体需要处理 |
| 子词 / BPE | 用数据学习常见片段，在词表与长度间折中 | 结果依赖语料和切分规则，增加预处理复杂度 |

词级方案还遇到边界问题：中英文词界不同，代码标识符和网络新词不断出现。如果所有未见词都变成 `UNK`，会丢失原文区别，往返还原和概率评价也会受影响。

字节级 BPE 保留全部基础字节，再加入频繁字节串。因此在保留这些字节、没有额外限制的前提下，未见词可以拆成较小片段，最终退回字节，无须把整词替换为 `UNK`。

原课的 tokenizer 示例还展示了：空格可能与后面的词合为一个 token，同一个词在句首和句中可能切法不同，数字也可能被拆成多段。这些是**特定分词器的行为**，不能当作所有模型的规则。

**讲义依据：`tokenization_examples`、`character_tokenizer`、`byte_tokenizer`、`word_tokenizer`、`bpe_tokenizer`。**

## 6. BPE 训练：学习合并规则 {#bpe-training}

BPE（Byte Pair Encoding）从较小单位出发，反复把频繁出现的相邻 token 对合成一个新 token。这里学习的是**词表和有先后顺序的合并规则**，并没有训练神经网络权重。

字节级版本的概念流程是：

1. 把训练文本转成 UTF-8 字节，以 256 个基础字节作为初始词表。
2. 统计当前 token 序列中的相邻对，选出频数最高的一对。
3. 分配新 ID；新 token 的字节内容是左右 token 字节内容的拼接。
4. 把该对的非重叠出现替换为新 ID，记录合并顺序。
5. 重新统计并继续，直到达到目标词表规模或没有可合并对。

**补充手算：**用 ASCII 文本 `abababab`，初始 ID 为 `a=97`、`b=98`。这里刻意只用一种重复模式，避免频数并列带来额外规则。

| 阶段 | 当前 token 序列 | 本轮最高频相邻对 | 新 token |
| --- | --- | --- | --- |
| 初始 | `a b a b a b a b` | `(a,b)` 出现 4 次 | `256 → b"ab"` |
| 第 1 次合并后 | `256 256 256 256` | `(256,256)` 出现 3 次 | `257 → b"abab"` |
| 第 2 次合并后 | `257 257` | 达到本例设定的 2 次合并 | 停止 |

第二轮统计得到 3 个相邻对，但实际只能从左到右做 **2 次非重叠替换**。这说明「相邻对的统计次数」与「替换次数」可能不同。

最终保留 256 个基础字节和 2 个新增 token，词表规模为 258；原来的 8 个字节现在只需 2 个 token。真实语料需要确定并列频数时的选取规则，才能使训练结果可复现。

**讲义依据：`BPETokenizerParams`、`train_bpe`、`count_adjacent_pairs`、`merge`。**手算语料和非重叠说明为补充；这里没有给出作业要求的实现代码。

## 7. BPE 编码、解码与边界 {#bpe-encoding}

训练得到规则后，编码新文本时使用固定规则，**不会每遇到一段新文本就重新训练词表**。

沿用上一节的两条规则：先合并 `(a,b) → 256`，再合并 `(256,256) → 257`。编码新文本 `ababac`：

~~~text
基础字节：a b a b a c
规则 1：  256 256 a c
规则 2：  257 a c
最终 ID：[257, 97, 99]
~~~

新出现的 `c` 没有对应的合并规则，仍可用基础字节 99 表示。解码时查词表并拼接：`b"abab" + b"a" + b"c"`，得到 `ababac`。

原课的教学实现按学习顺序遍历规则，便于观察每次变化；生产实现还需要更高效的候选管理。不要简单把 BPE 当成「在词表里贪心选最长字符串」，因为训练得到的合并优先级会影响切分。

原讲义指出完整 tokenizer 还需要处理两类边界：

- **预分词（pre-tokenization）：**先按约定切成片段，再在片段内进行 BPE。它约束可合并范围，也影响性能与切分习惯。
- **特殊 token：**文档边界等保留标记需要单独约定，不能让普通文本合并过程随意破坏。标记是否允许在输入中被识别，也要有明确策略。

**补充理解：**tokenizer 文件与模型权重应匹配。如果任意更换词表或 ID 映射，模型的嵌入和输出层不会自动知道新 ID 的含义。特殊 token 也不是权限机制；出现一个形似角色标记的普通字符串，不代表系统就应赋予其角色权限。

**讲义依据：`BPETokenizer.encode`、`BPETokenizer.decode`、`bpe_tokenizer`；匹配与权限说明为补充。**

## 8. 压缩率与模型计算的取舍 {#efficiency}

本讲定义的压缩率是 UTF-8 字节数除以 token 数：

$$
r=\frac{\text{UTF-8 字节数}}{\text{token 数}}.
$$

同一文本、同一字节编码下，$$r$$ 越大，token 序列越短。它不是 ZIP 文件压缩比，也没有把词表文件、ID 存储格式和元数据都计入。

以 `abababab` 为例，纯字节方案的比值为 $$8/8=1$$，两轮 BPE 后为 $$8/2=4$$。这说明在这段文本上序列缩短了，不证明它对所有语言或任务都更好。

**补充推导：**标准全注意力的序列两两交互部分随长度 $$T$$ 按 $$T^2$$ 增长。如果同一段原文从 1000 个 token 缩成 500 个，该部分的元素数从 100 万降到 25 万。整层成本还包含投影和 MLP，所以不能直接说完整训练一定快 4 倍。

扩大词表也有成本。隐藏维度为 $$d$$、词表大小为 $$V$$ 时，嵌入矩阵有 $$Vd$$ 个参数；输出层也受 $$V$$ 影响，是否共享权重要另算。词表过大还会包含大量低频片段，使统计与学习变稀疏。

| 选择 | 可能收益 | 需要检查 |
| --- | --- | --- |
| 增加合并与词表 | 缩短常见文本的序列 | 参数、输出计算、低频 token 的学习 |
| 保持较小词表 | 更充分共享基础单位 | 序列变长，注意力和生成步数增加 |
| 调整训练语料 | 改善目标语言或领域的切分 | 其他语言、代码和长尾输入的变化 |

因此应在目标数据上比较字节 / token、任务表现、实际吞吐和内存。不同 tokenizer 下的每 token loss / perplexity 单位不同，不能直接把数值高低当成语言建模能力的公平比较；可以补充按同一原文单位归一化的指标，并控制评估条件。

**讲义依据：`get_compression_ratio`、`tokenization_examples`、`tokenization`；参数公式、成本与评价边界为补充。**

## 9. 练习、术语与自测 {#review}

**补充练习：**仅用 Python 标准库运行第 4 节的 Unicode 算例，换成自己的中英文文本，记录码点数和 UTF-8 字节数。再手算第 6、7 节的 BPE 例子，检查每条规则和解码结果。它们用于理解概念，不是官方作业解答。

| 术语 | 本讲含义 |
| --- | --- |
| Token / token ID | 建模单位 / 词表中的整数索引 |
| Vocabulary | ID 与内容之间的映射 |
| Merge rank | 合并规则的优先级或学习顺序 |
| Byte-level BPE | 从基础字节出发学习频繁片段 |
| Round-trip | 编码再解码还原原文 |
| Pre-tokenization | 在 BPE 之前约定片段边界 |

<details>
<summary>1. 一个中文汉字一定是一个 token 吗？</summary>
<p>不一定。UTF-8 字节数由编码决定，token 数由具体词表和切分规则决定。一个汉字可以被拆开，多个汉字也可能合为一个 token。</p>
</details>

<details>
<summary>2. 在四个相同 token 中，相邻同型对有几次？能做几次非重叠替换？</summary>
<p>有 3 个相邻位置对，但一轮从左向右只能替换 2 次，因为每个原 token 不能同时参与两个替换。</p>
</details>

<details>
<summary>3. 遇到新词，为什么字节级 BPE 仍可编码？</summary>
<p>它保留全部基础字节。没有学到整体片段时，可以继续拆小，最终用 UTF-8 字节表示。编码阶段沿用已有规则，不重新训练。</p>
</details>

<details>
<summary>4. 把词表扩大到每句话一个 token，是不是最优？</summary>
<p>序列可能变短，但词表、参数和输出计算会迅速增长，绝大多数句子又是低频或未见的。需要同时看泛化、数据效率和系统成本。</p>
</details>

<details>
<summary>5. 分词器训练与语言模型训练分别学什么？</summary>
<p>本讲的 BPE 训练学习词表与有顺序的合并规则；语言模型训练学习神经网络参数，用于根据上下文预测 token 概率。两者的对象和目标不同。</p>
</details>
