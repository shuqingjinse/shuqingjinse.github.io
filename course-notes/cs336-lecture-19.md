## 1. 一次请求怎样变成输出 token {#lifetime}

这场课从训练完成之后讲起：模型只是运算图，真正把输入变成用户看到的结果，还要依靠路由、缓存、调度、分布式执行、kernel 和采样。

一次请求的大致路径是：**接收请求 → 分词 → 路由与查找可复用前缀 → prefill → 反复 decode 与采样 → 检查停止条件 → 返回结果**。服务运行时，这条路径会与许多其他请求交错，而不是让每个用户独占整个模型。

讲者特别说明，前半部分的若干系统示意图由生成式 AI 制作，细小文字和数字可能不准确。因此本笔记以可核对口述机制为主，不把示意图里的标签当成硬件规格。

**录像定位：[00:00–09:55](https://www.youtube.com/watch?v=9EEm4iMAF5s&t=0s)。**以下公式、算例和实验模板为本站补充，性能结论均须限定工作负载。

## 2. 先描述真实流量，再设计服务 {#workload}

生产流量和训练 batch 不一样，也未必符合工程师随手构造的均匀长度分布。代码智能体可能输入整段仓库上下文，再不断调用工具、追加信息；摘要可能长输入短输出；普通聊天又有另一种长度分布。

此外，还需记录会话多少轮、每轮间隔多久、用户多久回来。连续的工具循环需要缓存保持温热；几周后才继续的会话则很难一直占用 GPU 内存。

| 需要记录的量 | 为什么影响设计 |
| --- | --- |
| 输入 / 输出长度分布 | 决定 prefill 与 decode 的工作占比 |
| 轮数与轮间间隔 | 决定前缀复用与缓存保留价值 |
| 首 token 目标 | 限制排队、prefill 和缓存恢复时间 |
| 完整回答目标 | 约束生成速度与总响应时间 |
| 并发与突发性 | 决定容量、调度与尾延迟 |

补充例子：两项任务输入都为 10,000 token，一个只输出 20 token，另一个输出 2,000 token。即使模型相同，前者更强调快速处理长输入，后者还要长时间占用生成资源。不能只用一个平均长度代表两种流量。

**录像定位：[09:55–13:38](https://www.youtube.com/watch?v=9EEm4iMAF5s&t=595s)。**

## 3. Prefill、decode 与连续批处理 {#stages}

prefill 同时处理提示词中多个位置，工作形态更接近训练前向；decode 每次根据历史生成少量 token，小 batch 时更容易受权重和缓存搬运限制。这里说的是典型工作负载，batch、序列和 kernel 会改变瓶颈。

连续批处理让完成的请求退出，再接纳新请求，使设备不用等整批都完成。但每个请求不仅消耗计算，还占用 KV cache；有空闲算力却没有足够 cache 时，新请求仍可能排队。

将 prefill 与 decode 分配到不同 worker，可以分别优化，也能减少长 prefill 干扰短 decode。代价包括 KV 传输、路由复杂度和资源比例选择，因此分离不是任何规模下都自动更好。

补充核算：若两阶段理想处理时间分别为 $$t_p$$、$$t_d$$，分离后还要计入传输 $$t_x$$ 和排队 $$t_q$$。不能只因为某一阶段更快，就声称端到端的 $$t_p+t_d+t_x+t_q$$ 更小。

**录像定位：[13:38–22:13](https://www.youtube.com/watch?v=9EEm4iMAF5s&t=818s)。**

## 4. 多级 KV cache、缓存路由与可靠性 {#cache}

缓存可避免为同一前缀重复计算。常用数据结构可以查找已处理的 token 前缀，再只执行新加入的部分；并非任意两段内容相似就能共享同一份 KV。模型版本、位置和相关配置也要相容。

GPU 内存不足时，可以把部分缓存移到 CPU DRAM、SSD 或其他存储。空间增大了，恢复时间也增加，因而涉及迁出、预取和保留策略。讲者用操作系统的内存管理来建立直觉，而不是给出一个对所有流量最优的淘汰算法。

缓存感知路由进一步区分低命中率的新长请求与高命中率的温热会话，减少两类 prefill 相互干扰。收益来自真实请求分布，不能照搬一次实验的百分比。

系统正确性同样重要。讲者举例说明，少见的越界、未初始化内存、NaN 或工具停止条件错误，可能表现为重复 token、语言突变或异常长输出。应把这些当作需要定位的系统症状，而非仅凭表象推断模型训练数据或量化有问题。

补充排查顺序：固定输入复现 → 比较参考实现的中间值 → 检查 shape、mask、cache 索引和边界 → 确认工具与停止协议 → 扩大到变长并发。大规模服务还要考虑多 GPU 故障和长上下文跨卡处理。

**录像定位：[22:13–34:18](https://www.youtube.com/watch?v=9EEm4iMAF5s&t=1333s)。**

## 5. Megakernel：把 GPU 看成需要调度的系统 {#megakernel}

逐算子 kernel 便于编写和复用，却可能在启动、结束和尾部等待中浪费时间。长短任务不均时，少数 SM 仍在工作，其他 SM 已空闲，下一阶段又可能等待全部完成。

Megakernel 更积极地融合多个操作，并在内部安排带依赖的子任务。例如可在 QKV / RoPE 尚未全部完成时提前读取已有 KV cache，或在注意力结束前预取后续输出投影权重。**可以提前的是已知数据的搬运；依赖尚未产生的结果仍必须等待。**

这种思路把 kernel 优化扩展为细粒度的数据流与调度问题。ThunderKittens 等底层抽象帮助组织子 kernel、片上资源和同步，但融合范围越大，资源与正确性管理通常越困难。

补充性能模型：

$$
t\gtrsim\max\left(\frac{\text{FLOPs}}{\text{可用算力}},\frac{\text{搬运字节}}{\text{可用带宽}}\right)+\text{未隐藏的启动、同步与空闲}.
$$

这个式子用于定位数量级，不是精确模拟器。Megakernel 的收益可能来自最后一项和更好的重叠，并不是改变了模型的数学任务。具体实现的历史结果见[ThunderMLA 原始文章](https://hazyresearch.stanford.edu/blog/2025-03-04-thundermla)，不能推广为所有模型和硬件的固定加速比。

**录像定位：[34:18–41:35](https://www.youtube.com/watch?v=9EEm4iMAF5s&t=2058s)。**

## 6. Parcae：固定参数，增加循环计算 {#loop}

传统固定深度模型常通过增加参数或数据提高质量。循环 Transformer 让激活多次经过同一组层，复用权重，为计算量增加另一个旋钮。

补充的抽象写法为：

$$
h_{k+1}=F_\theta(h_k,x).
$$

重复的是执行，共享的是参数 $$\theta$$。因此参数存储可以保持不变，FLOPs 和延迟仍随循环增加。较小权重可能腾出更多 cache，或让模型跨越「能装入更少 GPU」的门槛，从而减少通信，但这需要实际系统验证。

讲者介绍的 Parcae 不是简单把任意模型多跑几次。直接循环训练可能出现 loss spike 和 NaN，必须分析与稳定化。字幕中项目名存在近音转写，本页按[原始论文 Parcae](https://arxiv.org/abs/2604.12946)校正。

**录像定位：[41:35–47:55](https://www.youtube.com/watch?v=9EEm4iMAF5s&t=2495s)。**

## 7. 稳定性、动力系统与扩展规律 {#stability}

讲者将残差流的循环变化视为动力系统，把复杂非线性变换与较简单的线性注入分开分析。忽略非线性项后的**补充线性示意**为：

$$
h_{k+1}=Ah_k+Bx,\qquad
h_K=A^Kh_0+\sum_{j=0}^{K-1}A^jBx.
$$

若某些方向随重复作用不断放大，就可能出现残差爆炸。论文通过对注入参数的参数化与离散化施加约束，改善稳定性；不能把「负对角矩阵」简化成任意离散矩阵只要对角为负就稳定。

还需区分**谱半径**与**谱范数**：前者是特征值绝对值的最大值，后者是最大奇异值，一般并不相等。在线性系统里，$$\rho(A)<1$$ 保证渐近衰减；非正规矩阵仍可能有瞬态放大，完整非线性训练则需更多条件。这里用数学定义澄清口述的简化直觉。

稳定以后，再研究循环次数、数据和参数的预算分配。课中结果提示，在特定实验范围内，固定参数而增加训练预算时，数据与循环次数共同增加可能优于只增加数据。这是带条件的经验扩展关系，不能推导出无限循环必然更好。

比较时必须说明固定了什么：参数、数据、训练 FLOPs 或推理成本。只固定参数与数据，循环模型可能实际用了更多计算；同 FLOPs 比较则需要调整其他变量。

**录像定位：[47:55–60:35](https://www.youtube.com/watch?v=9EEm4iMAF5s&t=2875s)；数学边界参照原论文并作补充说明。**

## 8. 问答：工程代价与硬件协同设计 {#questions}

| 问答主题 | 核心观点与边界 |
| --- | --- |
| 能否循环已有预训练模型？ | 有初步现象值得研究，不能当作任意模型无需训练就能提升的保证。 |
| 较少参数如何改善推理？ | 可留出更多 KV cache、减少跨卡通信；额外循环也有时间成本。 |
| Megakernel 的主要代价？ | 编写、调试和适配很耗人力，形状、batch、模型和硬件变化可能需要重做。 |
| 已知部署硬件怎样影响架构？ | 先看内存、缓存与可用计算格式，再决定尺寸、表示和执行方案。 |
| 计算最优是否意味着总应循环？ | 取决于 FLOPs、数据、参数、部署和目标质量的共同约束。 |
| 智能体与离线批处理哪里不同？ | 多轮智能体重视 cache 复用；一次性编码或批任务有另一组注意力与生成需求。 |
| 能否融合多 GPU 通信？ | 可研究融合通信与计算，但通信延迟仍可能成为瓶颈，局部融合与全模型融合的难度不同。 |

补充理解：硬件协同设计意味着在真实平台约束下选择模型与实现，不是将某家公司、精度格式或芯片宣称为普遍最优。本页不以课堂例子代替现时硬件规格或商业信息。

**录像定位：[60:46–71:28](https://www.youtube.com/watch?v=9EEm4iMAF5s&t=3646s)。**

## 9. 练习、自测与全课回顾 {#review}

补充项目：选择一个小模型，记录长短输入、不同 batch、缓存冷热下的延迟与显存。先用 profile 定位，再只改变一个缓存、调度或实现因素，报告何时有效、何时失效。

<details><summary>前缀缓存命中率高，为什么仍可能慢？</summary><p>可能需要从 CPU 或磁盘恢复缓存，或受排队、decode 带宽、通信与调度限制。命中减少重复计算，不消除所有服务成本。</p></details>
<details><summary>Megakernel 可以在 Q 产生之前完成依赖 Q 的注意力吗？</summary><p>不能。可提前搬运已有 K、V 或其他独立数据；真正依赖 Q 的计算仍需等待它产生，正确的数据依赖必须保留。</p></details>
<details><summary>谱半径与谱范数为什么不能混为一谈？</summary><p>它们分别由特征值和奇异值定义。矩阵可能渐近稳定却仍发生瞬态放大，不能靠一个口语化的「范数」覆盖全部分析。</p></details>
<details><summary>循环模型参数少，是否保证更低推理成本？</summary><p>不保证。权重和通信可能减少，循环执行仍增加计算与时间；要在目标质量、硬件和流量下测量。</p></details>

全课复习路径：**文本如何变成 token → 架构如何产生概率 → 训练需要多少算力与内存 → GPU、kernel 和多卡如何提高效率 → 如何安排模型与数据预算 → 如何评估、清理和混合数据 → 如何后训练与接入多模态 → 如何让服务在真实流量下可靠运行。**
